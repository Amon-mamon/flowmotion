# Contract — Flow Motion v1

Single source of truth. Owned by the architect. Status: DRAFT v1.

## 1. Scope
**In v1:** landing page, auth, dashboard; connect GitHub repo (read-only GitHub App); project validity check; safe file reading; security findings; automation recommendations; generate flows from selected recommendations; node canvas with inspector; mock-data simulation; n8n JSON export plus setup checklist.
**Out of v1:** running flows for users, user-facing live n8n testing (`n8n.md`; the dev/CI import test is in, D-9), subscription/billing/credit enforcement (`subscription.md`), team workspaces, non-GitHub sources, other export formats, Code nodes.

## 2. Core user flow
1. Land, sign up, go to `/dashboard`.
2. Install the GitHub App, then add a repository and choose which branch to analyze (default branch preselected, D-18).
3. Open a project, press Analyze.
4. See the validity result. Invalid projects stop here with a reason and no AI spend.
5. See security findings and the list of recommendations.
6. Select one or many recommendations, press Generate.
7. Open a flow: node canvas, click a node to inspect its parameters.
8. Run the test (mock data). See the level badge: Valid or Simulated.
9. Export n8n JSON plus the setup checklist.

## 3. Routes
- Marketing (public): `/`, `/privacy`, `/terms` — static pages. `/privacy` must state plainly that redacted snippets of the user's code are sent to the AI provider and that no source code is stored (`security.md` section 3).
- Auth: `/login`, `/signup` (pages, frontend; they call the browser Supabase client `signInWithPassword` / `signUp` directly, D-11), `GET /api/auth/callback` (Supabase code exchange, backend; configured as the Supabase redirect URL; on success redirects to `/dashboard`, on failure to `/login?error=auth`; never follows a `next` parameter), `POST /api/auth/sign-out` (backend; clears the session cookies, returns `{ signedOut: true }`; the frontend then navigates to `/login`). Sign-in method: email + password only in v1 (D-11). No password reset in Phase 1 (Phase 5).
- App (auth required): `/dashboard`, `/projects/[projectId]`, `/projects/[projectId]/analysis/[analysisId]`, `/flows/[flowId]`, `/settings` (display name, connected GitHub installations with disconnect; MFA enrolment added in Phase 5)
- Middleware (`src/proxy.ts`, Next.js 16 name for middleware, backend-owned, D-14): refreshes the Supabase session cookie on every matched request (`@supabase/ssr`); unauthenticated users visiting app pages go to `/login`; `/api/*` returns `401 UNAUTHORIZED` JSON instead of redirecting, except the browser-navigated `GET /api/github/install`, `GET /api/github/authorize` (Phase 1.1), and `GET /api/github/installations/callback`, which redirect to `/login`, and the sessionless `GET /api/auth/callback` and `POST /api/github/webhook`, which are not checked; authenticated users visiting `/login` or `/signup` go to `/dashboard`. Marketing pages are never redirected. Matcher excludes `_next/static`, `_next/image`, `favicon.ico`, and files with an extension.

## 4. Analysis pipeline (backend)
1. **Validate project (no AI).** Fetch the file tree (paths only) through the GitHub API **at the head commit of the branch recorded on the analysis** (`analyses.branch`, copied from `projects.branch` when the analysis is created; never the repo's default branch unless that is the chosen branch, D-18). Every later step reads files from that same tree. Valid if there is a strong marker of a website or app: `package.json` with a web or app framework (next, react, vue, svelte, nuxt, astro, express, fastify, nest, hono, react-native), `index.html` with assets, Python (django, flask, fastapi), Ruby (rails), PHP (laravel), Flutter `pubspec.yaml`, or a Go/Java/.NET web framework. Invalid: empty, docs-only, dotfiles-only, data-only, single script, no source. Output `{ kind: "website" | "app" | "invalid", reason }`. Stop on invalid.
2. **Select files.** Apply the path policy from `security.md` (deny first, then extension allowlist, size cap 200 KB per file, at most 400 files, prioritised: routes, API handlers, jobs, webhooks, CI files, manifests, schema files, README; exact tiers in the Phase 2 scope, section 11). Blocked files are counted by reason (`denied`, `extension`, `size`, and `cap` for allowed files beyond the 400-file limit), never fetched. The ordered list of selected files (`{ path, sha, size }`) is stored on the job row (`state.selected`) so later batches can resume.
3. **Fetch in batches, scan and redact.** Files are fetched in batches of **25** in priority order (one batch per worker step, see below). The secret scanner runs on every fetched file **inside the same step, before anything is written to `jobs.state`**, so raw file text never reaches the database. Matches become masked findings and are redacted (`[REDACTED]`) from text that goes onward. Static extractors (step 4) run on the redacted text in the same step. Redacted text is kept in `state` only for files that fit the prompt budget (step 5) and only while AI is enabled; it lives there only until the analysis ends (D-6).
4. **Static detection.** Deterministic extractors produce **signals** (`Signal`, section 6): routes, webhooks, cron or scheduled jobs, queue consumers, email/Slack/Discord/Telegram SDK usage, database writes, CI workflows, env var names used in code (names only). Signals are derived data (paths, names, cron expressions), never source text; they are saved on the analysis (`analyses.signals`) together with the findings by the `detect` step, so they survive even when the AI step is disabled or fails.
5. **AI analysis.** Runs only when the AI kill switch is off (`ANALYSIS_MODEL` set to a model id and `ANTHROPIC_API_KEY` set, section 10, D-16); otherwise the job skips this step and the analysis ends `done` with `error_code = AI_DISABLED` (findings and signals shown, no recommendations). The model is called through the provider interface in `src/lib/analysis/model/` (Anthropic adapter by default; a deterministic fake in every test). It receives signals and redacted snippets inside delimiters and returns `RecommendationDraft[]` (section 7), validated by Zod. The model has no tools. Drafts referencing node types outside `node-catalog.md` are dropped, not failed. **Token budget: at most 120k input tokens per analysis prompt** (estimated as `ceil(chars / 3)`, no tokenizer dependency). Files are included in priority order until the budget is hit; the rest are not sent and are counted as `files_skipped_budget`. One successful model call per analysis.
6. **Persist.** Save recommendations (findings and signals were saved by `detect`). Delete all temporary text, including the job's `state` blob. Mark the analysis done.

**Generation** (one job per selected recommendation): AI produces a `FlowSpec` (section 7), validated against the catalog; the compiler builds n8n JSON; the validator checks it; the simulator runs the `TestSpec`; save the result. The AI never writes n8n JSON. **Token budget: at most 30k input tokens per generation prompt.** A FlowSpec that fails Zod or the FlowSpec rules, an n8n JSON that fails the validator, or a simulation with failing cases or incomplete branch coverage sends the job back to `ai` (`testing.md`), at most twice, so the **total cost cap is 3 model calls per flow**. After the third call (OQ-13 default): if the validator never passed, the flow is `failed` with `error_code = GENERATION_EXHAUSTED`; if the validator passed but the simulation still fails, the flow is `ready` at level **Valid** with the last test run stored as `passed = false` so the failures are visible (`testing.md`, "never hidden").

### Background jobs (chunked state machine, Supabase only)
Supabase Edge Functions have a short wall-clock limit, so one invocation can never fetch 400 files and call the model. Every long job is a row in `jobs` (section 5) and runs as a resumable state machine. **One worker invocation does at most one step or one batch**, writes progress to the job row, and reschedules itself. No third-party queue.

- Analysis steps (`jobs.step`): `validate` → `select` → `fetch:N` (N = batch index, 25 files per batch, repeated until all selected files are fetched; each batch also scans, redacts, and extracts) → `scan` (path-based findings for denied secret files, dedupe and cap findings) → `detect` (dedupe signals, write findings and `analyses.signals`) → `ai` → `persist`. When AI is disabled, `detect` is followed directly by `persist`, which ends the analysis `done` with `error_code = AI_DISABLED`. Validation failure ends the job at `validate` with analysis status `rejected` and `error_code = PROJECT_INVALID`; the project gets `status = invalid`, `invalid_reason`, `stale = false`. On success `validate` sets the project `status = valid`, `invalid_reason = null`, `detected_kind`, `last_commit_sha = <head sha>`, `stale = false`, and `analyses.commit_sha`, `analyses.validation`. Both outcomes write `analyses.validation`.
- The `ai` step is tried at most **2 times** (not `max_attempts`) so a flaky provider can cost at most 2 billed calls; a `usage_events` row is written for every model response received.
- Generation steps: `ai` → `compile` → `validate` → `simulate` → `persist`. A failed `validate` or `simulate` goes back to `ai` and increments `state.model_calls` (max 3 in total, above; this counter is separate from `jobs.attempts`).
- **Per-step time budget: 20 seconds.** The `ai` step may take up to 60 seconds (one model call). A step that exceeds its budget aborts and the job is retried from the same step (the step must be idempotent).
- Progress: each step updates `jobs.step`, `jobs.state` (jsonb: selected paths, batch cursor, counts, redacted snippets while needed), `jobs.updated_at`, and the `analyses.progress` / `analyses.status` the user sees. Status mapping: `validate` → `validating`; `select`/`fetch`/`scan` → `scanning`; `detect`/`ai`/`persist` → `analyzing`. `progress` is an integer 0..100 that never decreases: `validate` 5, `select` 10, `fetch:N` spread evenly from 10 to 60, `scan` 65, `detect` 70, `ai` 75, `persist` 100. Generation jobs update `flows.status` only (`generating` → `ready` | `failed`).
- Scheduling: a `pg_cron` job runs every 10 seconds and invokes the worker Edge Function over HTTP (`pg_net`) with a service-role bearer token; the worker claims one job (section 5), executes one step, and if the job is not finished calls itself once more immediately (self-call) so the cron tick is only a safety net. The `POST .../analyze` and `.../generate` handlers insert the job row and trigger one worker call directly so the first step starts without waiting for the tick. **Poll kick (works without `pg_cron`):** `GET /api/analyses/:id` (and from Phase 3 `GET /api/flows/:id`) triggers one worker call (fire-and-forget) when the referenced job is `queued` with `run_after <= now()` and `updated_at` older than 15 seconds, or `running` with `locked_at` older than 2 minutes; so a chain broken by a failed self-call resumes while the user watches, and the cron tick is only needed for jobs nobody is polling. Trigger failures are logged by code only and never fail the request.
- Only the worker (service role) reads or writes `jobs.state`. The user-facing `GET /api/analyses/:id` reads only `analyses`.

## 5. Data model (Supabase, RLS on every table)
- `profiles(id → auth.users, display_name, created_at, updated_at)` — row created by the `auth.users` insert trigger (Phase 0); `display_name` 1..80 chars after trim or null
- `github_installations(id, user_id, installation_id bigint, account_login, created_at)` — `unique (user_id, installation_id)`: several Flow Motion users may link the same org installation, each proven through their own `GET /user/installations` check (section 6); `installation.deleted` removes every row with that `installation_id`. Phase 1.1 security fixes (D-22) add `github_user_id bigint null`, `github_user_login text null` (the GitHub account that linked the row; null only on rows linked before D-22), and `repos_synced_at timestamptz null` (time of the last successful repo access sync for this row; null = never synced or cleared, so a refresh is required)
- `github_installation_repos(user_id → auth.users, installation_id uuid → github_installations, repo_id bigint, repo_full_name text, private boolean, default_branch text, primary key (installation_id, repo_id))` (Phase 1.1 security fixes, D-22) — the repos of that installation **the linking GitHub user can access**, exactly as returned by `GET /user/installations/{id}/repositories` at the last sync. `(installation_id, user_id)` is a composite FK to `github_installations(id, user_id)` `on delete cascade`. Index on `user_id` and on `(installation_id, lower(repo_full_name))`. `repo_full_name` check: matches the repo full name rule in section 6. `default_branch` is display-only (the branches route returns the live default). Owner-only `select` RLS; no client writes; written only by `link_github_installations()` and the webhook (service role).
- `projects(id, user_id, installation_id nullable → github_installations, repo_full_name, repo_id bigint null /* Phase 1.1 security fixes: GitHub repo id, set by POST /api/projects; null on older rows */, default_branch, branch, status[pending|valid|invalid], invalid_reason, detected_kind[website|app], last_commit_sha, stale, created_at)` — `branch text not null` (Phase 1.1, D-18) is the branch the user chose and the only branch the pipeline and webhook use; check `char_length(branch) between 1 and 255`; it is fixed after creation (to use another branch the user adds the repo again). `default_branch` is the repo's GitHub default at creation time, kept for display only. `last_commit_sha` is the head of `branch`. `unique (user_id, repo_full_name, branch)` (replaces the Phase 1 `unique (user_id, repo_full_name)`), so the same repo may be added once per branch; the `installation_id` foreign key is the one exception to the cascade rule below: `on delete set null`, so `installation_id` becomes null when the GitHub installation is removed (webhook `installation.deleted`) or disconnected in `/settings`; the UI then asks the user to reconnect GitHub before analyzing
- `analyses(id, project_id, user_id, status[queued|validating|scanning|analyzing|done|failed|rejected], progress, branch, commit_sha, files_considered, files_read, files_blocked, files_blocked_by_reason jsonb, files_skipped_budget, validation jsonb null, signals jsonb, error_code, started_at, finished_at)` — `branch text not null` (Phase 1.1) is the branch analyzed, copied from `projects.branch` by `POST .../analyze`; `commit_sha` is that branch's head at `validate`; `files_blocked_by_reason` is `{ denied, extension, size, cap }` counts (`cap` added in Phase 2; readers treat a missing key as 0); `files_skipped_budget` counts files selected but not sent to the model because of the token budget (section 4; 0 when AI is disabled); `validation` is `{ kind, reason }` written by the `validate` step; `signals` is `Signal[]` (section 6, default `[]`, max 500) written by `detect`. A partial unique index on `analyses(project_id) where status in ('queued','validating','scanning','analyzing')` allows at most one active analysis per project (Phase 2 migration).
- `jobs(id, user_id, kind[analyze|generate], ref_id, status[queued|running|done|failed], step, state jsonb, attempts, max_attempts, run_after, locked_at, locked_by, last_error_code, created_at, updated_at)` — `ref_id` is the `analyses.id` or `flows.id`; `step` and `state` are the state machine cursor (section 4). `max_attempts` defaults to 5. `state` is cleared on `done` and `failed` so no repo text outlives the job.
- `security_findings(id, analysis_id, user_id, category, severity, file_path, line, masked_evidence, remediation)` — never raw secrets
- `security_findings.category` is one of the 11 categories in `security.md` section 6; `line` is null for path-only findings (a denied secret file that exists).
- `recommendations(id, analysis_id, user_id, title, description, trigger_kind, confidence, source_files text[], required_credentials text[], risk_level, node_types text[], rationale, estimated_tokens, status[new|selected|generated])` — `node_types` (full type names, for example `n8n-nodes-base.slack`) and `rationale` (1..400 chars) are added by the Phase 2 migration and come from the draft; Phase 3 generation uses `node_types` as a hint
- `flows(id, user_id, recommendation_id, name, flow_spec jsonb, n8n_json jsonb, setup_checklist jsonb, catalog_version, n8n_version, status[generating|ready|failed], error_code, created_at)` — `ready` means the validator passed (level at least Valid); the generation `persist` step also writes one `flow_test_runs` row
- `flow_test_runs(id, flow_id, user_id, level[valid|simulated], passed, results jsonb, simulator_version, created_at)` — `level = simulated` only when `passed = true` with 100% branch coverage (`testing.md`)
- `usage_events(id, user_id, kind[analysis|generation], tokens_in, tokens_out, ref_id, created_at)` — log only, no limits; `ref_id` is the analysis or flow id
- `audit_log(id, user_id, action, ref, created_at)`
- `rate_limits(key primary key, window_start, count)` — Postgres-based limiter; no RLS policies (service role only); incremented through the function `rate_limit_hit(p_key text, p_limit int) returns boolean` (atomic upsert `count + 1`, returns `count <= p_limit`; the window is part of the key, section 6 and `security.md` section 5); rows older than 48 h are purged by the `pg_cron` tick added in Phase 2

Every foreign key (except `projects.installation_id`, above) is `on delete cascade`, so deleting a project removes its analyses, findings, recommendations, flows, and test runs (`security.md` section 3). `projects.(installation_id, user_id)` is a composite FK to `github_installations(id, user_id)` (`on delete set null (installation_id)`), so a project's installation must belong to the same user. `jobs.ref_id` has no FK, so `DELETE /api/projects/:id` calls the service-role-only function `delete_project(p_user_id, p_project_id) returns boolean` (false when the project is not the user's), which in one transaction locks the project and its jobs, deletes the jobs for its analyses and flows, then deletes the project (the cascade removes the rest), so a worker step cannot resurrect rows.

**Migrations are append-only (D-19, from 2026-11-12).** The baseline and Phase 1 migrations are applied to the owner's hosted Supabase database, so **no existing file in `supabase/migrations/` is ever edited, renamed, or deleted**. Every schema change is a new migration with a later timestamp that is safe on a database already holding data (add columns nullable, backfill, then `set not null`; `if exists` / `if not exists` guards). Order from here: `20261113000000_phase1_1_project_branch.sql` (exists), then `<ts>_phase1_1_repo_access.sql` with `<ts>` later than `20261113000000` (for example `20261113120000`), then `<later ts>_phase2_analysis.sql` (later than the repo access migration, for example `20261114000000`).

**`link_github_installations(p_user_id uuid, p_github_user_id bigint, p_github_user_login text, p_installations jsonb) returns table (installation_id bigint, inserted boolean)`** (Phase 1.1 security fixes, D-22): `security definer`, `set search_path = ''`, `execute` revoked from `public`, `anon`, `authenticated` (service role only). `p_installations` is `[{ installationId: number, accountLogin: string, repos: [{ id: number, fullName: string, private: boolean, defaultBranch: string }] }]`. In one transaction: lock the user's `github_installations` rows `for update`; if any has a non-null `github_user_id` different from `p_github_user_id`, `raise exception 'github_account_mismatch'` (nothing written); upsert each installation on `(user_id, installation_id)` setting `account_login`, `github_user_id`, `github_user_login`, `repos_synced_at = now()`; for each, delete its `github_installation_repos` rows and insert the given repos (replace, never merge); for the user's other rows (not in `p_installations`), delete their repo rows and set `repos_synced_at = null`; return one row per given installation with `inserted = true` when the row was new. An empty `p_installations` only clears.

**RLS:** users can `select` rows where `user_id = auth.uid()`. Pipeline tables (`analyses`, `security_findings`, `recommendations`, `flows`, `flow_test_runs`, `jobs`) are written only by server code using the service role. On `jobs` the owner's `select` policy excludes the `state` column (expose it through a view or column grant, never to the client). The service role key is never imported in client code.

**Job claiming and retry:**
- Claim: in one transaction, `SELECT ... FROM jobs WHERE status = 'queued' AND run_after <= now() ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED`, then set `status = 'running'`, `locked_at = now()`, `locked_by = <worker invocation id>`, `attempts = attempts + 1`. Wrap this in a Postgres function (`claim_job()`) called by the worker.
- Stale lock: a `running` job with `locked_at` older than 2 minutes is treated as crashed and is re-queued by the next claim (same function).
- Retry and backoff: on a step error the worker sets `status = 'queued'`, `last_error_code`, and `run_after = now() + 30s * 2^(attempts - 1)` (30s, 60s, 120s, 240s). When `attempts >= max_attempts` the job becomes `failed` and the referenced analysis or flow is marked `failed` with the same `error_code`. Non-retryable errors (`PROJECT_INVALID`, `GITHUB_ACCESS_LOST`, `BRANCH_NOT_FOUND`, `MODEL_OUTPUT_INVALID` for analysis, `GENERATION_EXHAUSTED`) end the job immediately without backoff. `AI_DISABLED` is not an error: the job ends `done`.
- `claim_job(p_worker_id text) returns setof jobs` (0 or 1 row) is `security definer`, `execute` revoked from `public`, `anon`, `authenticated` (service role only).
- `attempts` counts tries of the **current step**. After a step succeeds the worker advances `step`, sets `status = 'queued'`, `run_after = now()`, `locked_at = null`, `attempts = 0`, and the next claim picks it up.

## 6. API (Next.js route handlers)
Envelope: `{ ok: true, data } | { ok: false, error: { code, message } }`. Every handler checks the session, validates input with Zod, and applies the rate limiter. **JSON keys are camelCase in every request and response** (database columns are snake_case; the backend maps at the boundary). Timestamps are ISO 8601 strings; ids are uuids unless stated. State-changing handlers (`POST`, `PATCH`, `DELETE`) reject requests whose `Origin` header is present and differs from the `APP_URL` origin with `403 FORBIDDEN` (CSRF guard; the webhook is exempt because it is verified by signature). **Branch names (`branchNameSchema`, Phase 1.1, git `check-ref-format --branch` rules):** a string of 1..255 characters (UTF-8 bytes ≤ 255) that is not `@`; no ASCII control characters (0x00–0x1F, 0x7F), space, `~`, `^`, `:`, `?`, `*`, `[`, `\`; does not contain `..`, `@{`, or `//`; does not start with `-` or `/`; does not end with `/`, `.`, or `.lock`; no `/`-separated segment starts with `.` or ends with `.lock`. Not trimmed (leading/trailing whitespace is already invalid). The name stored is the `name` GitHub returns for the branch. When a branch is placed in a GitHub API path it is encoded **per segment** (`name.split("/").map(encodeURIComponent).join("/")`), so `/` stays a literal path separator as GitHub's docs show for names like `feature/x` (the Phase 1 helper's single `encodeURIComponent(branch)` turns it into `%2F` and must change); a test covers a branch containing `/`.

**Repo full names (`repoFullNameSchema`, Phase 1.1 security fixes, D-23 / S11-4):** match `^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$`, at most 140 characters, and neither the owner nor the name segment equals `.` or `..`. Applied to every `repo` / `repoFullName` input and to every `full_name` taken from GitHub before it is stored (a GitHub item that fails is dropped and counted, not stored). `encodeRepoPath` rejects `.` / `..` segments as well (defence in depth).

**Repository access (Phase 1.1 security fixes, D-22).** A repo is **accessible** to the user through an installation row when (1) the row is the user's, (2) its `repos_synced_at` is not null and later than `now() - 24 hours` (OQ-20; the row is **fresh**), and (3) `github_installation_repos` has a row for that installation row whose `repo_id` matches (or, before a repo id is known, whose `lower(repo_full_name)` equals the requested name lowercased). Any failure of (2) or (3) is `GITHUB_REFRESH_REQUIRED` 403 with message "Refresh repository access to continue." It is checked **before** any GitHub call for the repo, so it reveals nothing about repos outside the set. The check is a shared helper `requireRepoAccess(userId, installationRowId, { repoId?, fullName })` in `src/server/github/repo-access.ts`. Read-only routes over the user's own derived data (`GET /api/projects*`, `GET /api/analyses/:id`, findings, recommendations, flows) do not check it.

The `analyses` array of `GET /api/projects/:id` is `{ id, status: AnalysisStatus, commitSha, errorCode: JobErrorCode | null, startedAt, finishedAt }[]`, newest first, at most 20.

**Daily caps (abuse protection, not billing):** per user per UTC day, at most **10 analyses** and **30 generations** (one per recommendation). Enforced server-side in the route handler through the `rate_limits` table (keys `daily:analyze:<user_id>:<yyyy-mm-dd>` and `daily:generate:<user_id>:<yyyy-mm-dd>`), before any job is queued. It resets at 00:00 UTC."`; the UI shows its own copy from `design.md` and may ignore the message). This is not a plan limit and must not be presented as one (`subscription.md` is NOT READY).

## 7. FlowSpec (internal flow format)
```ts
FlowSpec = {
  version: 1,
  name: string,
  description: string,
  nodes: { key: string, nodeType: AllowedNodeType, label: string,
           params: Record<string, JsonValue>,   // validated by the node's Zod schema from the catalog
           sourceFiles?: string[] }[],
  edges: { from: string, to: string, output?: number, input?: number }[],   // output index for IF / Switch (default 0); input index for Merge (default 0)
  requiredCredentials: { type: string, usedBy: string[] }[],   // type = credential name from node-catalog.md ("Slack", "SMTP", ...)
  tests: TestSpec                                            // see testing.md
}
```
Rules (checked by Zod plus a rule pass in the generation `ai` step; a failure counts as a failed model call): keys unique; exactly one trigger; every edge references existing keys, with `output`/`input` below the node's catalog output/input count; every node reachable from the trigger; no cycles except through `splitInBatches`; at most 40 nodes; only catalog node types; params only contain fields the catalog allows; URLs `https`; no secrets; placeholders must look like `YOUR_APP_URL` and appear in the checklist; expressions only from the supported subset (`testing.md`). These are the same rules the static validator applies to the compiled JSON (`testing.md`), so a FlowSpec that passes compiles to a Valid export.

### RecommendationDraft (analysis model output)
Zod schema in `src/schemas/recommendation.ts`. The model returns `RecommendationDraft[]` (max 20).
```ts
RecommendationDraft = {
  title: string,                       // 3..80 chars, plain text
  description: string,                 // 10..600 chars, plain text
  trigger_kind: "webhook" | "schedule" | "manual",
  confidence: number,                  // 0..1
  source_files: string[],              // must be paths that were actually sent to the model
  required_credentials: string[],      // catalog credential names (for example "Slack", "SMTP")
  risk_level: "low" | "medium" | "high",
  node_types: AllowedNodeType[],       // every entry must be in the catalog allowlist
  rationale: string                    // plain text, 10..400 chars
}
```
Rules: a draft whose `node_types` contains an unknown or excluded type is **dropped** (logged as a count, not an error); a draft that fails the schema in any other way is also dropped; the analysis fails (`MODEL_OUTPUT_INVALID`) only if the whole array fails to parse. Zero surviving drafts is a `done` analysis with no recommendations (the UI shows an honest empty state), not a failure. `source_files` entries not in the sent set are removed from the draft; `required_credentials` entries that are not catalog credential names (`SMTP`, `Slack`, `Discord`, `Telegram`, `Google`, `Notion`, `Airtable`, `GitHub`, `Postgres`, `Supabase`) are removed likewise. `node_types` are full names (`n8n-nodes-base.<type>`) checked against `src/lib/n8n-catalog/allowlist.ts`, which backend creates in Phase 2 from the type tables in `node-catalog.md` (the Phase 3 generator then checks it against the generated catalog). All strings are rendered as plain text, never HTML (`security.md` section 4). Surviving drafts become `recommendations` rows; `estimated_tokens` is computed by the backend, not the model.

## 8. n8n export format (compiler output)
```json
{ "name": "...",
  "nodes": [ { "id": "uuid", "name": "Unique Name", "type": "n8n-nodes-base.webhook",
               "typeVersion": 2, "position": [250, 300], "parameters": {} } ],
  "connections": { "Unique Name": { "main": [ [ { "node": "Next Name", "type": "main", "index": 0 } ] ] } },
  "settings": { "executionOrder": "v1" } }
```
- `type` and `typeVersion` come only from the generated catalog (`node-catalog.md`).
- Node `name` must be unique because `connections` are keyed by name.
- IF: output 0 is true, output 1 is false. Other multi-output nodes: meaning comes from catalog metadata.
- Positions are auto-laid-out left to right (about 220 px between columns).
- Credentials: never include ids or secrets. Placeholder format is open (OQ-6) until verified by the dev import test.
- The settings block, `typeVersion` values, and any top-level fields must be verified by importing into a real n8n. From Phase 3 this is done by the **dev-only / CI-only import test** (`n8n.md` section "Allowed now", D-9): a pinned n8n runs locally or in CI, every golden export from `tests/conformance/` is imported, and the test passes only if each opens with no errors. Exports carry an internal "unverified import" flag until that test passes for the pinned `n8n_version`; the flag is cleared when it passes and set again whenever the pin changes. Mechanism: the import test writes `tests/conformance/verified.json` (`{ n8nVersion, verifiedAt }`, committed); `importVerified = (verified.json.n8nVersion === pinned n8n version)` is computed by the backend and returned by `GET /api/flows/:id`; when false the export UI shows "Import into n8n x.y not yet verified" (plain notice, export still allowed). User-facing live testing stays NOT READY.

Invalid reasons (exact strings): no blobs → "The repository is empty."; only `.md`/`.txt`/`.rst` files or files under `docs/` → "The repository only contains documentation."; no file with a source extension (step 3 list minus `.json .yml .yaml .toml .md`) → "No source code was found."; otherwise → "No website or app framework was found. Flow Motion supports web and mobile app projects." Valid → `reason = null`. Tests: one fixture tree per marker and per invalid reason.
6. **File selection** `src/lib/analysis/select.ts` (pure): classify every blob (counts by reason), then order allowed files by tier, then path depth, then path (deterministic): (1) manifests and `.env.example`; (2) CI and schedulers: `.github/workflows/*`, `vercel.json`, `netlify.toml`, `Dockerfile`, `docker-compose*.yml`, `Procfile`, `supabase/functions/**`; (3) routes, handlers, webhooks, jobs: a path segment or basename matching `api|routes?|controllers?|handlers?|webhooks?|hooks|jobs?|workers?|queues?|cron|tasks?|functions|actions` or Next `route.(ts|js)` / `pages/api/**`, `urls.py`, `routes.rb`, `web.php`, `api.php`; (4) schemas: `*.prisma`, `**/migrations/*.sql`, `schema.*`, `models/**`, `*.graphql`; (5) root `README.md`; (6) other allowed files. Keep the first 400; the rest count as `cap`. `filesConsidered` = all blobs; `filesBlocked` = denied + extension + size + cap. Tests: tier order, determinism, caps, counts.
7. **Static extractors** `src/lib/analysis/extractors/*.ts` (pure, run on redacted text, regex based, one file per kind, at most 500 signals per analysis, dedupe on `(kind, filePath, label)`): `route` (Next `app/**/route.*` exported `GET|POST|PUT|PATCH|DELETE`, `pages/api/**`, Express/Fastify/Hono/Koa `app|router.<method>('…'`, Flask `@app.route`, FastAPI `@app.<method>`, Django `path('…'`, Rails `get|post '…'`, Laravel `Route::<method>`; label `"<METHOD> <path>"`); `webhook` (route paths or file names containing `webhook`, plus `stripe.webhooks.constructEvent`, `x-hub-signature`, `svix`); `schedule` (`vercel.json` `crons`, workflow `on.schedule.cron`, `node-cron` / `cron.schedule(`, Nest `@Cron(`, Celery beat, SQL `cron.schedule`; label = cron expression or `"schedule"`); `queue_consumer` (BullMQ `new Worker(`, `@Processor(`, `amqplib` `consume`, SQS `ReceiveMessage`, Celery `@shared_task`/`@app.task`, Sidekiq, Laravel `ShouldQueue`, Inngest / Trigger.dev functions); `messaging` (imports of `nodemailer`, `resend`, `@sendgrid/mail`, `postmark`, `@slack/web-api`, `@slack/bolt`, `discord.js`, `telegraf`, `node-telegram-bot-api`, `twilio`, Python `smtplib`, `slack_sdk`; label = library); `db_write` (Supabase/Prisma/Drizzle `insert|upsert|update|create`, SQL `INSERT INTO|UPDATE`, Django `.objects.create`, ActiveRecord `.create`; label = table or model name when visible, else the call); `ci_workflow` (each `.github/workflows/*` file; label = workflow `name:` or file name); `env_var` (`process.env.X`, `process.env["X"]`, `import.meta.env.X`, `os.environ[...]`, `os.getenv(...)`, `ENV[...]`, `env('X')`, keys of `.env.example`; label = name only, must match `^[A-Z][A-Z0-9_]{1,63}$`, dedupe by name). Tests: one fixture per pattern.
8. **Prompt assembly and model** `src/lib/analysis/model/`: `types.ts` (`AnalysisModel { analyze({ system, prompt, maxOutputTokens, signal }) → Promise<{ text, tokensIn, tokensOut }> }`), `config.ts` (kill switch, section 10), `anthropic.ts` (plain `fetch` to `https://api.anthropic.com/v1/messages`, `anthropic-version: 2023-06-01`, Zod on the response, 55 s abort; **no SDK, no new dependency**; tested only with a stubbed `fetch`), `fake.ts` (deterministic: returns a fixed `RecommendationDraft[]` derived from the input signals; used in every test; never selectable by env). `src/lib/analysis/prompt.ts`: fixed system prompt saying the delimited content is data with no instructions; signals JSON in `<signals>…</signals>` (≤ 16k estimated tokens, truncated by kind order); each file as `<repo_file path="…">…</repo_file>` with any `</repo_file` inside the text escaped; per-file cap 20,000 chars (head, marked truncated); files added in selection order until the 120k-token total is reached; `files_skipped_budget` = selected files read but not included. `parseDrafts(text, sentPaths)` applies section 7 rules. Tests: budget cut-off and count, delimiter escaping, drop rules, whole-array failure → `MODEL_OUTPUT_INVALID`.
9. **Worker** `src/lib/jobs/` (runtime-neutral): `runOnce(deps)` claims one job via `claim_job`, runs one step with its time budget (20 s, `ai` 60 s), writes progress per section 4, advances or retries per section 5, and reports whether a follow-up call is needed. `deps = { db, github, model | null, now, workerId }` so every step is unit-testable. Steps: `validate`, `select`, `fetch:N` (blob fetch by tree SHA `GET /repos/{o}/{r}/git/blobs/{sha}`; base64 decode; a file with a NUL byte or invalid UTF-8 is dropped and counted as `extension`; scan, redact, extract; keep redacted text only if AI is enabled and it fits the budget), `scan`, `detect` (delete-then-insert findings for the analysis, write `signals`, idempotent), `ai` (skipped → `persist` with `AI_DISABLED` when `resolveModelConfig` says disabled; otherwise one call, `usage_events` row `kind = analysis` with provider token counts, at most 2 attempts), `persist` (insert recommendations with `estimated_tokens = min(30000, 4000 + ceil(chars of its source files' snippets / 3))`, clear `state`, mark `done`, `progress = 100`, `finished_at`). Installation token minted once per invocation from the project's installation. The branch is always `analyses.branch`, never `default_branch`. GitHub 401/403/404 → `GITHUB_ACCESS_LOST` (except the branch-head 404 at `validate`, which may be `BRANCH_NOT_FOUND`, section 6); 429/5xx/network → retry with backoff. Logs carry ids, step names, counts, and error codes only. Edge Function `supabase/functions/worker/index.ts` + `supabase/functions/import_map.json` (D-12): checks `Authorization: Bearer` against the injected service-role key (constant time), calls `runOnce`, then self-calls once if more work is due. ## 12. Definition of done for v1
