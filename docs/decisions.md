# Decisions

Format: `D-n [date] decision — reason`

- **D-1** Flow Motion generates and exports flows. It does not run them. — Avoids building a workflow engine.
- **D-2** The AI never writes n8n JSON. It writes a FlowSpec from the allowed catalog; our compiler writes the JSON. — Prevents format mismatches.
- **D-3** Allowed nodes come from a generated catalog pinned to one n8n version. — Exports must match n8n.
- **D-4** Testing is an in-house mock-data simulator with honest levels (Valid, Simulated). — Users want proof without live credentials; live n8n testing is parked.
- **D-5** GitHub only, read-only GitHub App. — Smallest permission surface.
- **D-6** No source code is stored; only derived results. — Privacy and security.
- **D-7** Subscription and n8n live testing are NOT READY. — Test the product first.
- **D-8** Stack: Next.js, Supabase, Zod, react-hook-form, TanStack Query, Zustand, shadcn/ui, Motion, React Flow. — Owner's choice plus React Flow for the canvas.
- **D-9** [2026-11-10] A dev-only and CI-only n8n import test is allowed from Phase 3: the team runs a pinned n8n locally or in CI, imports every golden export from `tests/conformance/`, and confirms it opens with no errors. User-facing live testing stays NOT READY. — The export is the paid deliverable and must be proven to import; this is internal tooling with no user data and no customer-facing n8n. OQ-5 (licence) stays open and the owner must confirm it before public launch.
- **D-10** [2026-11-10] Background jobs (resolves OQ-4): a `jobs` table plus a Supabase Edge Function worker, run as a chunked, resumable state machine. One worker invocation does at most one step or one 25-file batch, writes progress to the job row, and reschedules itself (`pg_cron` tick every 10 s plus an immediate self-call). Per-step budget 20 s (60 s for the model call). Claiming uses `FOR UPDATE SKIP LOCKED`; retries use exponential backoff up to 5 attempts per step. — Edge Functions have a short wall-clock limit, so one invocation cannot fetch 400 files and call the model; this keeps the design Supabase-only with no third-party queue.
- **D-11** [2026-11-10] Sign-in (resolves OQ-15): Supabase Auth email + password only. No social login, no "Continue with GitHub". The GitHub App installation is a separate step after sign-in and is never a sign-in method. Sign-up and sign-in run in the browser through the Supabase client (anon key); email confirmation stays at the Supabase project default (on in production) and lands on `GET /api/auth/callback`. Password reset is not in Phase 1; it is added in Phase 5. — Smallest auth surface; keeps the GitHub App permissions read-only and separate from identity; a GitHub provider can be added later without touching the App flow.
- **D-12** [2026-11-10] Worker runtime (OQ-16 default recorded): the job worker is a Supabase Edge Function (Deno) that imports `src/lib/**` and `src/schemas/**` through `supabase/functions/import_map.json`; those folders stay runtime-neutral (`contract.md` section 9). Phase 1 code written in `src/lib/github/**` must already follow this rule (Web Crypto for the App JWT, `fetch` only). If the import map proves unworkable in Phase 2, the fallback in OQ-16 applies and the architect records a new decision. — Keeps one copy of the pipeline code; decided now so Phase 1 GitHub helpers are reusable by the worker.
- **D-13** [2026-11-10] Hosting (resolves OQ-17): Vercel, Node runtime for all route handlers and `src/proxy.ts`; no route handler does long work (all long work is in the worker). `APP_URL` is the public origin of the deployment. — Default Next.js host; timeouts are irrelevant because long work lives in Supabase.
- **D-14** [2026-11-10] Next.js 16 conventions (resolves OQ-18): the auth middleware is `src/proxy.ts` (`export function proxy`), backend-owned; `cacheComponents` stays off in v1; the shadcn v4 "base-nova" preset (Base UI primitives, `cn` package) is kept and the frontend adds components with `npx shadcn@latest add <name>`. **The AGENTS.md ownership row still says `src/middleware.ts`; only the owner edits that root file.** — Matches the framework version pinned in Phase 0; the owner's file is out of the architect's paths.
- **D-15** [2026-11-10] Phase 0 dependencies outside the AGENTS.md stack list are approved as pinned (full list in `requests.md`, 2026-11-10 entry). — Each is a direct consequence of the fixed stack (shadcn v4 preset, react-hook-form + Zod bridge, test runner, Tailwind v4 via Turbopack).
- **D-16** [2026-11-12] No paid AI budget yet (owner constraint). (a) The analysis model sits behind a small provider interface in `src/lib/analysis/model/` (`AnalysisModel.analyze`), with an Anthropic adapter (plain `fetch`, no SDK) as the default (OQ-3) and a deterministic fake used in every test; no other provider, SDK, or env name is added. (b) Steps `validate`, `select`, `fetch`, `scan`, `detect`, `persist` never depend on the model. (c) Kill switch, reusing existing names: AI is enabled only when `ANALYSIS_MODEL` is a model id other than `disabled` and `ANTHROPIC_API_KEY` is set; `ANALYSIS_MODEL=disabled` is the default in `.env.example` and in all environments until OQ-19 is answered; a missing worker secret counts as disabled. With AI disabled the job skips `ai` and the analysis ends `done` with `error_code = AI_DISABLED`; findings and signals are saved and shown, and the UI says "AI analysis is not enabled yet". (d) The `ai` step is tried at most 2 times so a flaky provider cannot multiply cost. — The product stays useful and fully testable with zero AI spend, and turning AI on later is one secret change.
- **D-17** [2026-11-12] Phase 2 pipeline details: findings and `analyses.signals` (derived data: paths, names, cron expressions, never source text) are written by the `detect` step so they survive a disabled or failed AI step; the scanner runs inside each `fetch:N` step before anything reaches `jobs.state`; files beyond the 400 cap are counted under a new `cap` reason; each analysis stores its own `validation`; at most one active analysis per project (partial unique index); a new non-retryable job code `GITHUB_ACCESS_LOST`; token budget estimated as `ceil(chars / 3)`; a "poll kick" in `GET /api/analyses/:id` re-triggers the worker so the chain does not depend on `pg_cron`. The worker stays a Supabase Edge Function (D-10, D-12). — Keeps the user honest counts and results without AI, keeps raw text out of the database, and lets the owner test without cron set up.
- **D-18** [2026-11-13, owner request] Branch selection: when adding a repository the user chooses the branch (default branch preselected). `projects.branch text not null` (1..255 chars, git ref-name rules via `branchNameSchema`, must exist on GitHub at creation) is the only branch the pipeline and the `push` webhook use; `default_branch` stays for display; `analyses.branch` records the branch each analysis used. Uniqueness is `(user_id, repo_full_name, branch)`, so one repo can be added once per branch (default applied, owner may override). The branch cannot be changed after creation in v1; the user deletes and re-adds (default applied). A chosen branch later deleted on GitHub ends the analysis `failed` with the new non-retryable `BRANCH_NOT_FOUND`. Built as Phase 1.1 before Phase 2 resumes. — Lets users analyze the branch they actually deploy from; immutability keeps analyses, findings, and stale tracking tied to one branch with no migration of history.
- **D-19** [2026-11-13] Migrations are append-only: the baseline and Phase 1 migrations are applied to the owner's hosted Supabase database, so existing files in `supabase/migrations/` are never edited, renamed, or deleted. Each change is a new, later-timestamped, data-safe migration (nullable add, backfill, then `not null`). — Editing applied migrations silently diverges the hosted schema from the repo.
- **D-20** [2026-11-13] GitHub link fallback (owner testing found the callback failing silently when the App was installed directly on GitHub or was already installed): new `GET /api/github/authorize` runs GitHub App user authorization with our own `state` cookie; a callback without `state` ignores its `code` and redirects there; a callback with a valid `state` binds every installation of this App that `GET /user/installations` returns for the user (and still requires a given `installation_id` to be in that list). The UI gets a "Link existing installation" link. — Simplest design that stays secure: ownership is always proven by a user token obtained under our own state, and it needs no new env name or table.
- **D-21** [2026-11-13] Launch requirement (amends D-11): before real users, Supabase Auth "Confirm email" must be on with custom SMTP configured; the signup page shows a specific message for the Supabase email rate limit. — The built-in mailer is rate-limited and for testing only; owner testing hit the limit.
- **D-22** [2026-11-13, resolves S11-1; amends D-20] **Per-user, per-repo access set.** Linking an installation proves only that the GitHub user can reach at least one of its repos, so every repo-scoped action now requires that the repo is in the user's own access set. (a) In the callback, while the one-time user token is in memory, the backend calls `GET /user` (GitHub user id and login) and, for each installation from `GET /user/installations`, `GET /user/installations/{installation_id}/repositories` (paged), which GitHub evaluates for that user (owner, collaborator, team, org base permission). The results are written atomically by one service-role SQL function into the new table `github_installation_repos` (one row per user, installation row, repo) and `github_installations.repos_synced_at`. The token is then discarded and never stored. (b) The repos list is served from this table; the branches route, `POST /api/projects`, and `POST /api/projects/:id/analyze` require the repo to be in the set and the set to be **fresh** (`repos_synced_at` within 24 hours), else the new error `GITHUB_REFRESH_REQUIRED` (403). (c) The user refreshes through the existing `GET /api/github/authorize` round trip ("Refresh repository access"); a refresh replaces the set (never merges) and clears the set of any linked installation the GitHub user can no longer see. (d) Webhook `installation_repositories`: `removed` deletes those repo ids from every user's set for that installation; `added` does nothing until each user refreshes. `installation.deleted` cascades. (e) Each `github_installations` row records `github_user_id` and `github_user_login` of the GitHub account that linked it. A Flow Motion user is bound to one GitHub account at a time: a callback from a different GitHub account than the one recorded on any existing row binds nothing and redirects to `?error=github_account`; to switch accounts the user disconnects the existing installations in `/settings` first. Rows linked before D-22 have no set and no GitHub user id, so they need a refresh before any repo action. **Alternative rejected:** checking `GET /repos/{o}/{r}/collaborators/{username}/permission` with the installation token on each request is always fresh, but it depends on a stored, renamable login, may need extra App permissions, adds a GitHub call per request, reports `read` for any public repo, and does not model org SSO; GitHub's own user-token evaluation is authoritative and needs no new permission. Also rejected: binding only installations on the user's own account or orgs where they are admin (breaks normal org members). — Simplest design that enforces GitHub's real per-user access on the server, keeps the user token one-time, and bounds revocation lag to 24 hours (owner may change the window, OQ-20).
- **D-23** [2026-11-13] Phase 1.1 review dispositions. **S11-3 fix:** a callback without our `state` no longer redirects to `/api/github/authorize`; it redirects to `/dashboard?link=github`, where the user clicks "Link existing installation", and `/api/github/authorize` refuses requests with `Sec-Fetch-Site: cross-site` (redirect `/dashboard?error=github`) — the fix is two small changes and removes the silent cross-linking chain that D-22 would otherwise turn into repo access. **S11-4 fix:** repo full names must match `^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$` with neither segment equal to `.` or `..` (schema and path encoder). **S11-5 fix:** a rate-limited `/api/github/authorize` or `/api/github/install` redirects to `/dashboard?error=github`, never JSON. **S11-6 accepted** until the D-21 launch gate (Confirm email on hides account existence). **R11-1:** the signup rate-limit copy in `design.md` is confirmed exactly as written (code `over_email_send_rate_limit` or HTTP 429). **R11-4:** the login rate-limit copy "Too many attempts. Please wait a moment and try again." is added to `design.md`. **R11-5 accepted** residual risk (`security.md` section 5). — Smallest changes that close each finding; the accepted items leak at most "an address has a recent pending signup" and are gated by D-21.
