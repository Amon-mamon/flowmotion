# Security — rules and leak list

Flow Motion reads other people's code, so security is a core feature. Owned by the architect. Reviewed by `security-reviewer`.

## 1. Never read secret files
Path policy runs **before** any fetch. Order: deny list, then extension allowlist, then size cap.

**Deny (never fetch, never open):** `.env`, `.env.*` (except the single exact basename `.env.example`, see below), `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `id_rsa*`, `id_ed25519*`, `*.ppk`, `.npmrc`, `.pypirc`, `.netrc`, `.git-credentials`, `.aws/`, `.ssh/`, `.gcloud/`, `.kube/`, `.docker/config.json`, `*credentials*`, `*secret*`, `*secrets*`, `service-account*.json`, `*.tfstate`, `*.tfstate.backup`, `terraform.tfvars`, `*.tfvars`, `*.sqlite`, `*.db`, `*.dump`, and (D-31, S2-7) `.yarnrc.yml`, `auth.json` (any directory, including `.composer/auth.json`), `credentials.json`, `.htpasswd`, `.pgpass`, `wp-config.php`, `*.p8`; `.git/`, `node_modules/`, lockfile bodies, build output, binaries, archives, images, media.
**Allow (examples):** source code, `package.json`, framework configs, route/handler files, CI workflow files, schema files, README.
**Explicit exception — `.env.example`:** the deny glob `.env.*` has exactly one exception: a file whose basename is exactly `.env.example` (case-sensitive, any directory) passes the path policy because it holds variable names only. It is still fetched through the normal pipeline and **still goes through the secret scanner**; any match there becomes a finding like any other file. Every other `.env.*` name stays denied: `.env.local`, `.env.production`, `.env.example.bak`, `.env.sample`, `.env.example.local`, `env.example` (no leading dot is not an env file but is also not the exception), `.ENV.EXAMPLE`.
**Broad globs block ordinary files:** `*secret*`, `*credentials*`, `*secrets*` will also deny ordinary source such as `secrets-manager-client.ts` or `credentialsForm.tsx`. This is intended (deny first, no exceptions beyond `.env.example`), but the analysis must stay honest about it: blocked files are counted by reason (`denied`, `extension`, `size`) and files dropped by the token budget as `budget`, and the analysis UI shows these counts grouped by reason (`contract.md` section 6, `GET /api/analyses/:id` counts).
**Matching:** paths are normalised first (`\` → `/`, leading `./` stripped, `.`/`..` resolved; a path escaping the root is denied); deny globs match case-insensitively against every path segment, so a denied directory name denies everything under it. Lockfiles, build/vendor dirs, `*.min.js`, and `*.map` are denied too (exact list in `contract.md` section 11, Phase 2 scope, backend item 3).
**If a denied file exists:** report only its existence ("an env file is committed") with a masked finding. Do not open it.
**Required path-policy tests** (every pattern above plus): `./.env`, `a/../.env`, uppercase variants, `.env.local`, Windows separators (`sub\.env`), `.env.example` allowed at root and in a subdirectory, `.env.example.bak` and `.env.sample` denied, `.ENV.EXAMPLE` denied, and a test that `.env.example` content is passed to the secret scanner.

## 2. Secret scanner (content level)
Runs on every file that was fetched. Patterns include: AWS keys, GitHub tokens, Slack tokens and webhook URLs, Stripe keys, Google API keys, private key blocks, JWTs, database URLs with passwords, generic high-entropy strings next to words like key, token, secret, password. The base patterns are listed in `contract.md` section 11 (Phase 2 backend item 4); the additions below (D-28, S2-2) are required **before any AI provider is enabled** (Phase 2b).

**Generic assignment rule (quoted and unquoted).**
- *Name:* the variable or key name contains, case-insensitively, `key`, `token`, `secret`, `password`, `passwd`, `pwd`, `passphrase`, `credential`, or `auth`, or ends with `_pass` (D-34). *Password-type names* are the subset whose name contains `password`, `passwd`, `pwd`, `passphrase`, or `secret`, or ends with `_pass` (all case-insensitive).
- *Quoted form (any fetched file):* `NAME` followed by `=`, `:`, `=>`, or `:=` and a value in `"…"`, `'…'`, or `` `…` ``.
- *Unquoted form (config files only):* basename `.env.example`, extensions `.yml` `.yaml` `.toml`, basename `Dockerfile`, basename `Procfile`, and any `docker-compose*.yml` / `compose*.yml` or `.github/workflows/*` file. Line shapes: `NAME=VALUE` or `NAME: VALUE` at line start (after optional indentation), optionally prefixed by `export ` or `- ` (compose `environment:` lists, CI `env:` blocks); Dockerfile `ENV NAME=VALUE`, `ENV NAME VALUE`, `ARG NAME=VALUE`. `VALUE` is the run of characters up to the first whitespace, quote, or ` #` comment. Not applied to source code, where an unquoted value is an expression (`apiKey: process.env.OPENAI_API_KEY`).
- *Value extent (D-33, S2R-1; amended by D-34, R2b-1):* no upper length bound. A quoted value runs to its closing quote on the same line. For a **password-type name** the quoted value may contain spaces and tabs (never a line break or any of the three quote characters), so `const password = "correct horse battery staple 99";` is one value; for **every other name** a quoted value containing whitespace does not match (so `authError: "Authentication failed, please retry"` and `title = "hello world example text here"` give no finding). An unquoted value ends at its natural end as defined above (no spaces for any name). The placeholder, entropy, base32 and minimum-length rules below apply to the whole value including its spaces, and when a value is accepted the whole value is replaced by `[REDACTED]` (never only a prefix). The work must stay linear (an unterminated quote with spaces after a password-type name in a 200 KB file scans in well under a second).
- *Match:* the value is at least 20 characters with Shannon entropy ≥ 3.5, **or** it is base32-shaped (`^[A-Z2-7]{16,}={0,6}$` with at least one digit `2`-`7`, for example a TOTP seed; entropy not required, D-33), **or** it matches a provider pattern below (provider patterns also run on their own over all text).
- Category `hardcoded_secret` (`ci_secret` in CI, Dockerfile, compose; `client_exposed_secret` per the existing `NEXT_PUBLIC_` rule; `jwt_signing_secret` when the name contains `JWT` or `SESSION`).

**Provider patterns (all fetched files, quoted or not; category `hardcoded_secret` unless the CI or client rule applies; masked type in parentheses):**
| Provider | Pattern (regex, case-sensitive) |
|---|---|
| Anthropic (`Anthropic key`) | `\bsk-ant-[A-Za-z0-9_-]{20,}` |
| OpenRouter (`OpenRouter key`) | `\bsk-or-[A-Za-z0-9_-]{32,}` |
| OpenAI (`OpenAI key`) | `\bsk-(?!ant-\|or-)(?:proj-\|svcacct-\|admin-)?[A-Za-z0-9_-]{32,}` (checked after the two above) |
| SendGrid (`SendGrid key`) | `\bSG\.[A-Za-z0-9_-]{16,32}\.[A-Za-z0-9_-]{30,64}` |
| npm (`npm token`) | `\bnpm_[A-Za-z0-9]{36}\b` |
| GitLab (`GitLab token`) | `\bglpat-[A-Za-z0-9_-]{20,}` |
| Supabase (`Supabase service key`) | a JWT (existing pattern) whose decoded payload has `"role":"service_role"`; `\bsb_secret_[A-Za-z0-9_-]{20,}`. `sb_publishable_…` and anon JWTs are public and never match. |
| Twilio (`Twilio key`) | API key `\bSK[0-9a-fA-F]{32}\b`; auth tokens through the generic rule (`TWILIO_AUTH_TOKEN`) |
| Mailgun (`Mailgun key`) | `\bkey-[0-9a-f]{32}\b`; `\b[0-9a-f]{32}-[0-9a-f]{8}-[0-9a-f]{8}\b` |
| Postmark (`Postmark token`) | a UUID assigned (quoted or unquoted) to a name containing `POSTMARK` (any case), or following `X-Postmark-Server-Token` / `X-Postmark-Account-Token`; entropy not required |
| Resend (`Resend key`) | `\bre_[A-Za-z0-9]{6,12}_[A-Za-z0-9]{16,40}\b` with entropy ≥ 3.5 on the part after `re_` (avoids Python `re_` identifiers) |

**Placeholders never match (every pattern above and the generic rule; amended by D-33 / S2R-1):** an empty value; a value starting with `your-` or `your_`; a value containing `changeme`, `example`, or `xxx` **as a whole word** (case-insensitive; `xxx` = a run of 3 or more `x`; the word must be bounded on both sides by the start or end of the value or a non-alphanumeric character, so `sk-or-v1-xxxx…` and `example-key` are placeholders but a random `…aXxXb…` is not); a value wrapped in `<…>`; a value containing `${` or `{{`, or starting with `$` (variable and CI secret references such as `${{ secrets.X }}`); a value made of one repeated character (for a provider pattern, the part after its literal prefix and after an optional `v<digits>-` version segment, so `sk-or-v1-` + 64 `0` is a placeholder, D-34). **Generic rule only:** a bare variable name, meaning the value matches `^[A-Z][A-Z0-9_]*$`, contains at least one `_`, and is under 20 characters or has entropy < 3.5 (so `OTHER_VAR` is skipped, but `JBSWY3DPEHPK3PXP…` or `ABCD1234EFGH5678…` is not). Accepted consequence (D-34, R2b-4): most real names of 20+ characters score ≥ 3.5, so `const tokenEnv = "STRIPE_SECRET_KEY_PRODUCTION"` is reported and redacted (fails safe).

**Tests (mandatory, AGENTS rule 11):** for every provider pattern and both generic forms, one positive case and one placeholder case that must **not** match; unquoted cases for `.env.example`, compose `environment:` list, YAML `password: …`, Dockerfile `ENV`/`ARG`, and a workflow `env:` block; a TypeScript `apiKey: process.env.X` line that must not match; `sk-ant-`/`sk-or-` reported as Anthropic/OpenRouter, not OpenAI; `sb_publishable_` and an anon JWT not matched; raw values absent from findings and redacted text. **D-33 / S2R-1 additions:** the positive and negative cases listed in `contract.md` section 11 Phase 2b backend item 5 (uppercase and base32 values, 600-character quoted and 700-character unquoted values fully redacted, provider and generic tokens containing a non-word `xxx`, and the whole-word placeholders). **D-34 additions:** the cases in `contract.md` section 11 "Phase 2b review fixes" item 1 (quoted passphrase with spaces found and wholly redacted; UI strings with spaces under non-password names not found), the long bare-name case, and the zero-filled `sk-or-v1-` placeholder.
**Path-only findings for the D-31 deny entries** (file never opened, `line = null`, evidence `"file present (not opened)"`; in addition to the list in `contract.md` section 11 Phase 2 item 4): `.yarnrc.yml`, `credentials.json`, `.htpasswd`, `wp-config.php`, and `auth.json` at the repo root or under `.composer/` → `hardcoded_secret`; `.pgpass` → `db_connection_string`; `*.p8` → `private_key`. `auth.json` elsewhere is denied without a finding.

- A match creates a finding with `masked_evidence` (first 2 and last 2 characters at most, or just the type) and `[REDACTED]` replaces it in anything sent to the model.
- The scanner must never log or store the raw value. It runs in the same worker step that fetched the file, **before** anything is written to `jobs.state`, so only redacted text ever reaches the database (`contract.md` section 4).
- Manifests read by the validity check (`package.json` and similar) are parsed in memory for dependency names only, never stored or logged.
- The same scanner runs on every generated flow before export.

## 3. Data handling
- Fetch files with the GitHub API using a read-only GitHub App (Contents: read, Metadata: read). No write permissions, no OAuth user tokens with broad scope.
- Installation tokens are short-lived and created on demand from the app private key. Store only `installation_id`.
- Installation ownership: the install link (signed-in users only) carries a random `state`; the httpOnly, secure, `sameSite=lax` cookie `fm_gh_state` (10-minute max-age, single use) holds `<userId>.<state>`. The callback requires the cookie's user id to equal the session user and its state to equal the query `state` (both constant-time), clears the cookie on every outcome, redirects every failure to `/dashboard?error=github`, exchanges the GitHub `code` for a user token (GitHub App "request user authorization", no extra scopes), checks the `installation_id` appears in `GET /user/installations`, and discards the token at once. User tokens are never stored. This stops one user from claiming another account's installation id (`contract.md` section 6).
- **Linking installations made on GitHub (Phase 1.1, D-20):** a callback without our `state` (App installed or reconfigured directly on GitHub) never binds anything and never uses the `code` it received, because that code is not tied to this browser's session (an attacker could otherwise plant their own code). It redirects to `GET /api/github/authorize`, which sets a fresh `fm_gh_state` cookie and sends the user through GitHub App user authorization (`/login/oauth/authorize`, no scopes) back to the same callback with our `state`. With a valid state the callback binds **only** installations returned by `GET /user/installations` for that user token, i.e. installations of this App the GitHub user can actually access, and since Phase 1.2 (D-43) only those on the user's own account or on an organization. Same cookie rules, same `?error=github` on any failure, token discarded at once. **Phase 1.1 security fixes (D-23 / S11-3):** a no-state callback redirects to `/dashboard?link=github` and the user must click "Link existing installation" (never an automatic authorize hop), and `/api/github/authorize` refuses `Sec-Fetch-Site: cross-site` requests, so a cross-site page cannot silently bind the browser's GitHub identity to the browser's Flow Motion user.
- **Per-user, per-repo access (Phase 1.1 security fixes, D-22 / S11-1):** an installation link proves only that the GitHub user can reach **at least one** of its repos, and installation tokens can read every repo in the installation. So the installation alone never authorizes a repo. While the one-time user token is in memory, the callback stores the repos that `GET /user/installations/{id}/repositories` returns for that user in `github_installation_repos` (owner-only RLS select, service-role writes) and the linking GitHub user id on the installation row; then the token is discarded. The repos list, branches route, `POST /api/projects`, and analyze all require the repo to be in that set and the set to be synced within 24 hours, checked server-side before any GitHub call for the repo; otherwise `GITHUB_REFRESH_REQUIRED` and the user re-runs `/api/github/authorize`. A refresh replaces the set, never merges it. Webhook `installation_repositories` `removed` deletes repos from every user's set at once; `added` grants nothing until the user refreshes. A Flow Motion user is bound to one GitHub account: a callback from a different GitHub user id binds nothing. **Residual:** a user removed from an org or repo on GitHub keeps access in Flow Motion for at most 24 hours (OQ-20), and keeps reading their own already-derived results (findings, recommendations, flows) for projects they created.
- **Which installations may be linked (Phase 1.2, D-43):** `GET /user/installations` also returns **another person's personal-account installation** whenever the user is a collaborator on one of its repos; linking those let a teammate see the owner's installation (owner live test). A user now links an installation only when its account is (a) the authorizing GitHub user's own account (`type = User` and account id equal to the id from `GET /user`; logins are never compared) or (b) an `Organization`. Every other installation (another person's `User` account, `Enterprise`, `Bot`, unknown, unparseable) is skipped before its repos are fetched. Enforced three times: the backend filter, `link_github_installations()` (`installation_not_allowed`, nothing written), and the table check constraint `github_installations_linkable_account`. Rows linked before Phase 1.2 are unclassified: the Phase 1.2 migration clears their repo sets (no repo access until refresh), and the next refresh deletes any of them GitHub no longer lists as linkable (their projects keep past results with `installation_id = null`, D-45). **Residual (accepted):** an outside collaborator on one repo of an organization still links that organization's installation, but sees and can use only the repos GitHub returns for them in `GET /user/installations/{id}/repositories` (the per-user access set, D-22), plus the organization's login in their installation list. Org members are covered the same way.
- **One GitHub account per Flow Motion account (Phase 1.2, D-44):** a GitHub account is held by the Flow Motion user who has at least one installation row with its GitHub user id. A callback from a GitHub account held by another Flow Motion user binds nothing and redirects to `/dashboard?error=github_in_use`; the check runs inside `link_github_installations()` under a per-GitHub-account advisory lock, so two concurrent links cannot both succeed. The account is released when the holder's last row is gone (Disconnect of every installation, uninstall on GitHub via the `installation.deleted` webhook, or a refresh that deletes the last row linked before Phase 1.2). A refresh that merely does not list a classified row only clears it, so it keeps holding the account. The notice never names the other Flow Motion account; it only tells the person who just proved control of the GitHub account that it is linked elsewhere. Together with `github_account_mismatch` this keeps the mapping one to one.
- **Repo full names are user input (D-23 / S11-4):** `^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$`, no `.` or `..` segment, also enforced in the GitHub path encoder.
- **Branch names are user input (Phase 1.1):** validated with `branchNameSchema` (`contract.md` section 6) before any use, confirmed to exist through the GitHub API before a project is created, placed in GitHub API paths only with per-segment encoding, never used in shell commands, file paths, or URLs other than `api.github.com`, and rendered as plain text.
- **Do not store source code.** Keep only derived results: recommendations, masked findings, flows. Delete temporary text when the analysis ends.
- **Job state TTL (D-29, S2-5):** a job not `done`/`failed` whose `updated_at` is older than 1 hour is failed with `JOB_EXPIRED` and its `state` cleared by `expire_stale_jobs()` (run by every `claim_job()`, the poll kick, and the analyze route). So redacted snippets in `jobs.state` outlive a broken chain by about an hour plus the time until the next worker call or poll.
- **Worker bearer (D-30, S2-6):** the worker Edge Function accepts only `Authorization: Bearer <WORKER_TOKEN>` (dedicated random token, at least 64 hex characters, constant-time compare, missing or short token = reject everything). The service-role key is never used as a bearer and never stored in Vault.
- **Local worker scope (D-27, R2-2):** the in-process development worker claims only jobs of the user whose request triggered it (`claim_job(p_worker_id, p_user_id)`), so a laptop running `next dev` against a shared database never processes other users' analyses.
- Never log file contents, model prompts, or model outputs containing repo text. Log ids, counts, and error codes only.
- **AI failure log (Phase 2c, D-35; narrowed in Phase 2d, D-36):** every failed model call or unusable model output (not a step-budget abort or a database error, which are `INTERNAL` with no line) writes one server log line `ai.failed` with exactly `{ jobId, attempt, reason, status, elapsedMs }` (`reason` is a fixed enum, `status` an HTTP status or null). It never contains the provider name, the model id, an error message, a request or response body, the prompt, snippets, or any key, and it is never stored in a table or returned in a DTO. Users see only the job code (`AI_UNAVAILABLE`, `MODEL_OUTPUT_INVALID`, `INTERNAL`).
- Tell users plainly (privacy page) that redacted snippets are sent to the AI provider. Check the provider's retention terms before launch.
- **AI provider choice (D-16, OQ-19):** no provider may receive real users' code if its terms allow training on submitted data or retention beyond what `/privacy` states. Free-tier hosted APIs commonly allow this, so they are acceptable only for the owner's own test repositories, never for real users. The AI kill switch (`contract.md` section 10) stays on until the owner has chosen a provider that meets this rule.
- **OpenRouter is development only (D-24, Phase 2b):** free OpenRouter endpoints (and some paid upstream providers behind it) may log prompts or train on them, so `ANALYSIS_PROVIDER=openrouter` is for the owner's own test repositories only, never real users' code. Enforced in code, fail closed: `resolveModelConfig(env, runner)` refuses `openrouter` unless `runner === "local"` (only the in-process `next dev` runner, which claims only the triggering user's jobs, D-27; the worker Edge Function always passes `"edge"` and so refuses unconditionally, D-33 / S2R-2), and also when `NODE_ENV=production` or `APP_URL` is not `localhost` / `127.0.0.1` / `[::1]` (the analysis ends `AI_DISABLED`). OpenRouter values live in `.env.local` only and are never set as worker function secrets. `OPENROUTER_API_KEY` is server-only (never `NEXT_PUBLIC_`, never logged, never in errors). The adapter sends no identifying headers. Anthropic stays the only production provider, so `/privacy` does not change; OQ-12 (Anthropic retention in writing) still gates launch. Launch checklist: no environment that serves real users has `ANALYSIS_PROVIDER=openrouter` or an `OPENROUTER_API_KEY`.
- Project repo coverage: `POST /api/projects` accepts a repo only if `GET /repos/{owner}/{repo}/installation` (App JWT) returns the caller's own installation id, since an installation token can read any public repo. The composite FK `projects(installation_id, user_id)` keeps a project's installation owned by the same user.
- "Delete my data": removing a project deletes its analyses, findings, recommendations, flows, test runs, and jobs in one transaction (service-role-only `delete_project()`, `contract.md` section 5).

## 4. Untrusted repo content (prompt injection)
- Repo text is data. Wrap it in clear delimiters and tell the model it contains no instructions.
- The analysis and generation models have **no tools** and cannot fetch URLs.
- All model output goes through Zod. Free text from the model is rendered as plain text, never as HTML.
- Never execute, install, or build anything from a user repo.
- Never fetch URLs found in repo content (SSRF). The only outbound calls are to the GitHub API, the AI provider (`api.anthropic.com`; `openrouter.ai` in development only, D-24), and Supabase.

## 5. Application security
- Supabase RLS on every table; tests that user A cannot read or write user B's rows.
- Service role key only in server code. Never in `NEXT_PUBLIC_*`.
- Zod validation on every API input and on env at startup.
- Postgres-based rate limits (`rate_limits` table, fixed 1-minute windows, keys `rl:<route>:<user_id|ip>:<window>`), error `RATE_LIMITED` 429. Defaults until Phase 5 tunes them: 120/min per user on all `/api/*`; 10/min per user on analyze, generate, test, export; 20/min per IP on `/api/auth/*`, `/api/github/install`, `/api/github/authorize`, and the installations callback; 60/min per IP on the webhook.
- Phase 3b limits: `POST /api/recommendations/generate` and `GET /api/flows/:id/export` 10/min per user (routes `generate`, `export`); `GET /api/flows` and `GET /api/flows/:id` use the general 120/min.
- Per-user daily caps as abuse protection, not billing: 10 analyses and 30 generations per user per UTC day, enforced server-side through the `rate_limits` table before a job is queued, error code `DAILY_CAP_REACHED` (`contract.md` section 6). Not a plan limit; `subscription.md` is NOT READY.
- Verify the GitHub webhook signature with a constant-time compare.
- CSRF protection for state-changing routes: `POST`/`PATCH`/`DELETE` handlers reject a request whose `Origin` header is present and is not the `APP_URL` origin (`403 FORBIDDEN`; the signature-verified webhook is exempt); secure, httpOnly, sameSite cookies.
- Security headers: CSP, HSTS, X-Content-Type-Options, frame-ancestors none, strict referrer policy.
- Generic error messages to users; details only in server logs, without secrets.
- Audit log for connect, analyze, generate, export, delete.
- **Email confirmation (launch requirement, D-21):** before real users, Supabase Auth "Confirm email" is on and custom SMTP is configured (the built-in Supabase mailer is rate-limited and meant for testing). Tracked in the launch checklist in `status.md`. **Accepted until this gate (D-23):** S11-6, while "Confirm email" is off the browser's direct Supabase sign-up response reveals whether an address already has an account. **Accepted residual risk (D-23, R11-5):** Supabase returns `over_email_send_rate_limit` for the per-address resend cooldown too, so signing up again within about 60 s with an address that has a pending unconfirmed signup shows the rate-limit message; this weakly reveals a recent pending signup and the client cannot tell the cases apart.
- **GitHub App setting (owner):** "Request user authorization (OAuth) during installation" must stay on; the callback needs its `code` for the ownership check and the repo access sync (D-22).
- Offer MFA. Pin dependencies, run `npm audit` in review, commit the lockfile.
- Exported flows: no secrets, no credentials ids, no Code or command nodes, preview and warnings before export. v1 profiles offer no delete or overwrite operation; flows that write data or send messages carry a checklist warning. Full rules in section 9.

## 6. Leaks Flow Motion must detect in the user's repo
| Category | Examples | Severity |
|---|---|---|
| committed_env_file | `.env`, `.env.production` present | high |
| hardcoded_secret | API keys, tokens, passwords in code | high |
| private_key | PEM/SSH/PGP private keys | high |
| cloud_credentials | AWS, GCP, Azure keys or config | high |
| service_account | service-account JSON | high |
| db_connection_string | URL with embedded password | high |
| jwt_signing_secret | hardcoded JWT or session secret | high |
| webhook_secret_url | webhook URLs with embedded tokens (Slack, Discord) | medium |
| ci_secret | secrets written into workflow files, Dockerfiles, compose | high |
| client_exposed_secret | service-role or secret keys used in browser code, or `NEXT_PUBLIC_` secrets | high |
| debug_config | debug mode or verbose logging committed for production | low |
Later (not v1): secrets in git history. Each finding has a category, severity, file path, line, masked evidence, and a remediation sentence (rotate the key, move to environment variables).

## 7. Leaks Flow Motion must prevent in itself
Secrets in generated flows, logs, error messages, analytics, or screenshots · model output exposing repo data across users · one customer seeing another's data (RLS) · leaked GitHub app key or service role key · forged GitHub webhooks · prompt-injected exfiltration · raw findings shown unmasked · source retained in jobs, caches, or backups · AI provider retaining code beyond stated terms · over-broad GitHub permissions.

`security-reviewer` runs after phases 2 to 5 (for Phase 3: after 3a and again after 3b) and writes `docs/security-review.md`. Release requires no open high or medium items.

## 9. Generated flows and export (Phase 3, D-39, D-40)
The model that writes a flow has read untrusted repo text, so its output is treated as hostile until our code has checked it. The model never writes n8n JSON; it writes a `FlowSpecDraft` that must pass strict Zod schemas and rules `F1`..`F12`, the compiler writes the JSON, and the validator checks the JSON again without trusting the compiler (`contract.md` sections 7 and 8, `testing.md`).

**Nothing from the repo or the model can become executable.**
- Only allowlisted node types (`node-catalog.md`); no Code, command, file, SSH, or sub-workflow nodes exist in the catalog, the profiles, or the compiler.
- Every node's `params` must match that node's strict profile schema: unknown keys fail, so the model cannot set an n8n parameter Flow Motion did not design for (for example an authentication option, a raw SQL query, or a "send binary" switch).
- **Expressions:** n8n evaluates any string parameter that starts with `=`. A `Text` value may not start with `=`; only the compiler adds that prefix, and only to text whose every `{{ … }}` parses with the small grammar in `contract.md` section 7 (field reads and one comparison; no calls, no `$env`, `$execution`, `$workflow`, `$vars`, `$secrets`, no arithmetic). The validator re-parses every `=` string in the compiled JSON. Text that fails is rejected, never "cleaned".
- Postgres and Supabase nodes take a table and column list as identifiers (`^[a-z_][a-z0-9_]{0,62}$`); there is no raw SQL operation.

**No secrets and no credentials in an export.**
- No node carries a `credentials` key, a credential id, a token, or a password. Credentials are named in the setup checklist and connected by the user inside n8n.
- HTTP headers named `authorization`, `proxy-authorization`, `cookie`, or `x-api-key` are rejected.
- The secret scanner runs over the serialized FlowSpec (`F9`), over the compiled JSON (validator rule 7), and once more in `assertExportSafe` on every download (with the no-`credentials` check and the 256 KB size limit); a hit refuses the export with `EXPORT_NOT_VALID` and logs the flow id and rule only.
- **Destinations are placeholders only.** Email addresses, Slack channels, chat ids, document, base, database, and repository ids, and every HTTP origin are `YOUR_…` tokens; a literal is a schema failure. So a repository cannot steer a generated flow into sending the user's data to an address or host of the repository author's choosing, and no literal host means no SSRF target ships in an export. Every placeholder is listed in the checklist (validator rule 9). No `http://` URL anywhere.

**Generation re-reads repo files (the `context` step).** It reads only the recommendation's own `source_files` (at most 12) at the analyzed commit, after the same per-user repository access check as analyze (`GITHUB_REFRESH_REQUIRED`), the S2-1 repo identity check, and the path policy; each file goes through the secret scanner before anything is written to `jobs.state`; only redacted text is kept, only in `jobs.state`, cleared when the job ends and by the 1-hour TTL (D-29). A denied path is never fetched even if the model listed it. The recommendation's title, description, and rationale are model text derived from repo text and are sent to the generation model inside delimiters as data. Retry feedback contains only rule ids and node keys produced by our code.

**AI provider and cost.** Generation uses the same provider switch as analysis; OpenRouter stays local-runner-only (D-33) and the Edge worker refuses it. At most 3 model calls are started per flow, counted before each call. `ai.failed` lines follow the rule in section 3 (five fixed keys, no prompt, no provider name). `/privacy` already states that redacted snippets go to the AI provider; generation sends nothing of a new kind.

**Serving the export and the canvas.** `GET /api/flows/:id` and `/export` return only the caller's own flow (`NOT_FOUND` otherwise); the export is served as an attachment with `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`; `flow.generate` and `flow.export` are written to the audit log. All flow text (name, labels, params, notes, checklist entries) is rendered as plain text in the canvas, inspector, and checklist. The dev import test runs a pinned n8n with no user data and no credentials and is never deployed (`n8n.md`); `n8n-nodes-base` is fetched to a temporary directory with `--ignore-scripts` and is never a project dependency.
