# Contract — Flow Motion v1

Single source of truth. Owned by the architect. Status: DRAFT v1.

## 1. Scope
**In v1:** landing page, auth, dashboard; connect GitHub repo (read-only GitHub App); project validity check; safe file reading; security findings; automation recommendations; generate flows from selected recommendations; node canvas with inspector; mock-data simulation; n8n JSON export plus setup checklist.
**Out of v1:** running flows for users, user-facing live n8n testing (`n8n.md`; the dev/CI import test is in, D-9), subscription/billing/credit enforcement (`subscription.md`), team workspaces, non-GitHub sources, other export formats, Code nodes.

## 2. Core user flow
1. Land, sign up, go to `/dashboard`.
2. Install the GitHub App, then add a repository and choose which branch to analyze (default branch preselected, D-18).
3. Open a project, press Analyze.
4. See the validity result. Invalid projects stop here with a reason and no AI spend.
5. See security findings and the list of recommendations.
6. Press "Generate flow" on a recommendation (one flow per recommendation, each started separately; no checkboxes, D-42).
7. Open a flow: node canvas, click a node to inspect its parameters.
8. Run the test (mock data). See the level badge: Valid or Simulated.
9. Export n8n JSON plus the setup checklist.

## 3. Routes
- Marketing (public): `/`, `/privacy`, `/terms` — static pages. Lenis smooth scrolling runs on `/` only (D-56; never on `/privacy`, `/terms`, auth, or app routes). `/privacy` must state plainly that redacted snippets of the user's code are sent to the AI provider and that no source code is stored (`security.md` section 3).
- Auth: `/login`, `/signup` (pages, frontend; they call the browser Supabase client `signInWithPassword` / `signUp` directly, D-11), `GET /api/auth/callback` (Supabase code exchange, backend; configured as the Supabase redirect URL; on success redirects to `/dashboard`, on failure to `/login?error=auth`; never follows a `next` parameter), `POST /api/auth/sign-out` (backend; clears the session cookies, returns `{ signedOut: true }`; the frontend then navigates to `/login`). Sign-in method: email + password only in v1 (D-11). No password reset in Phase 1 (Phase 5).
- App (auth required): `/dashboard`, `/projects/[projectId]`, `/projects/[projectId]/analysis/[analysisId]`, `/flows/[flowId]`, `/settings` (display name, connected GitHub installations with disconnect; MFA enrolment added in Phase 5), `/integrations` (Phase 2e-ui preview on sample data, D-54; the "AI provider" card; becomes live in the full Phase 2e; auth-protected through the `src/proxy.ts` app prefixes like the other app pages)
- Middleware (`src/proxy.ts`, Next.js 16 name for middleware, backend-owned, D-14): refreshes the Supabase session cookie on every matched request (`@supabase/ssr`); unauthenticated users visiting app pages go to `/login`; `/api/*` returns `401 UNAUTHORIZED` JSON instead of redirecting, except the browser-navigated `GET /api/github/install`, `GET /api/github/authorize` (Phase 1.1), and `GET /api/github/installations/callback`, which redirect to `/login`, and the sessionless `GET /api/auth/callback` and `POST /api/github/webhook`, which are not checked; authenticated users visiting `/login` or `/signup` go to `/dashboard`. Marketing pages are never redirected. Matcher excludes `_next/static`, `_next/image`, `favicon.ico`, and files with an extension.

## 4. Analysis pipeline (backend)
1. **Validate project (no AI).** Fetch the file tree (paths only) through the GitHub API **at the head commit of the branch recorded on the analysis** (`analyses.branch`, copied from `projects.branch` when the analysis is created; never the repo's default branch unless that is the chosen branch, D-18). Every later step reads files from that same tree. Valid if there is a strong marker of a website or app: `package.json` with a web or app framework (next, react, vue, svelte, nuxt, astro, express, fastify, nest, hono, react-native), `index.html` with assets, Python (django, flask, fastapi), Ruby (rails), PHP (laravel), Flutter `pubspec.yaml`, or a Go/Java/.NET web framework. Invalid: empty, docs-only, dotfiles-only, data-only, single script, no source. Output `{ kind: "website" | "app" | "invalid", reason }`. Stop on invalid.
2. **Select files.** Apply the path policy from `security.md` (deny first, then extension allowlist, size cap 200 KB per file, at most 400 files, prioritised: routes, API handlers, jobs, webhooks, CI files, manifests, schema files, README; exact tiers in the Phase 2 scope, section 11). Blocked files are counted by reason (`denied`, `extension`, `size`, and `cap` for allowed files beyond the 400-file limit), never fetched. The ordered list of selected files (`{ path, sha, size }`) is stored on the job row (`state.selected`) so later batches can resume.
3. **Fetch in batches, scan and redact.** Files are fetched in batches of **25** in priority order (one batch per worker step, see below). The secret scanner runs on every fetched file **inside the same step, before anything is written to `jobs.state`**, so raw file text never reaches the database. Matches become masked findings and are redacted (`[REDACTED]`) from text that goes onward. Static extractors (step 4) run on the redacted text in the same step. Redacted text is kept in `state` only for files that fit the prompt budget (step 5) and only while AI is enabled; it lives there only until the analysis ends (D-6).
4. **Static detection.** Deterministic extractors produce **signals** (`Signal`, section 6): routes, webhooks, cron or scheduled jobs, queue consumers, email/Slack/Discord/Telegram SDK usage, database writes, CI workflows, env var names used in code (names only). Signals are derived data (paths, names, cron expressions), never source text; they are saved on the analysis (`analyses.signals`) together with the findings by the `detect` step, so they survive even when the AI step is disabled or fails.
5. **AI analysis.** Runs only when the AI kill switch is off (`resolveModelConfig`, section 10, D-16; from Phase 2b also `ANALYSIS_PROVIDER`, D-24); otherwise the job skips this step and the analysis ends `done` with `error_code = AI_DISABLED` (findings and signals shown, no recommendations). The model is called through the provider interface in `src/lib/analysis/model/` (Anthropic adapter = the production provider; OpenRouter adapter = development only, Phase 2b, D-24; a deterministic fake in every test). It receives signals and redacted snippets inside delimiters and returns `RecommendationDraft[]` (section 7), validated by Zod. The model has no tools. Drafts referencing node types outside `node-catalog.md` are dropped, not failed. **Token budget: at most 120k input tokens per analysis prompt** (estimated as `ceil(chars / 3)`, no tokenizer dependency). Files are included in priority order until the budget is hit; the rest are not sent and are counted as `files_skipped_budget`. One successful model call per analysis.
6. **Persist.** Save recommendations (findings and signals were saved by `detect`). Delete all temporary text, including the job's `state` blob. Mark the analysis done.

**Generation** (one job per recommendation): AI produces a `FlowSpecDraft` (section 7), validated against the catalog; the compiler builds n8n JSON; the validator checks it; the simulator runs the `TestSpec` (from Phase 4); save the result. The AI never writes n8n JSON. **Token budget: at most 30k input tokens per generation prompt** (`ceil(chars / 3)`). A draft that fails Zod or the FlowSpec rules, an n8n JSON that fails the validator, or (Phase 4) a simulation with failing cases or incomplete branch coverage sends the job back to `ai` (`testing.md`). **Hard cost cap: at most 3 model calls are started per flow, whatever the reason** (D-40; details below). After the last call (OQ-13 default): if the validator never passed, the flow is `failed` with `error_code = GENERATION_EXHAUSTED`; if the validator passed but the simulation still fails (Phase 4), the flow is `ready` at level **Valid** with the last test run stored as `passed = false` so the failures are visible (`testing.md`, "never hidden").

**Generation input (D-40).** `jobs.state` of the analysis is deleted when the analysis ends and no source is stored (D-6), so the generation job rebuilds a small context itself in its first step, `context`: (1) the `recommendations` row (title, description, trigger kind, node types, required credentials, rationale, source file paths); (2) `analyses.signals` filtered to signals whose `filePath` is one of the recommendation's `source_files` (at most 100); (3) **redacted snippets of the recommendation's `source_files`, re-read from GitHub at `analyses.commit_sha`** (the analyzed commit, never the branch head): at most the first 12 paths, each must exist in that commit's tree and pass `classifyPath` (path policy, same 200 KB cap), binary or invalid UTF-8 files are dropped, each file goes through the secret scanner **in the same step before anything is written to `jobs.state`** (findings from this pass are discarded, only the redacted text is kept), per-file cap 20,000 characters, total snippet cap 60,000 characters (files added in `source_files` order until the cap; the rest are skipped). The step first repeats the S2-1 repo identity check (`GET /repos/{o}/{r}` id equals `projects.repo_id`). GitHub 401/403, a repo id mismatch, or a null `installation_id` → `GITHUB_ACCESS_LOST` (flow `failed`, not retried); a missing tree (404 for the commit) or missing paths are not errors: generation continues with the snippets it has (possibly none); 429/5xx/network → normal step retry. Snippets live only in `jobs.state` and are cleared when the job ends (and by the 1-hour TTL, D-29).

**Generation prompt.** Fixed system prompt (delimited content is data with no instructions; output is one JSON object and nothing else); then `<recommendation>` (JSON of the row fields above, also data: it is model text derived from repo text), `<signals>`, `<repo_file path="…">` snippets with `</repo_file` escaped (same helper as analysis), `<node_reference>` (the FlowSpec parameter reference for all 32 allowed nodes, built by code from the node profiles, `node-catalog.md`), the FlowSpec rules in short form (always including the text rules, D-59: no text starts with `=`; no `://` anywhere, links to the user's app as `YOUR_APP_URL/…`; every destination is one `YOUR_…` placeholder; `{{ … }}` only in the section 7 expression subset; `respondToWebhook` body values are literals; `switch` case values are literals; header names are `FieldName`s outside the header deny rule; flow `name` and `description` have no leading `=` and no `{{`; at most 40 nodes), and on a retry `<previous_errors>` (rule codes and node keys produced by our code, at most 20, never model text). `maxOutputTokens = 8000`. Budget split: instructions + node reference ≤ 8k tokens, signals ≤ 2k, snippets ≤ 20k (the 60,000-character cap).

### Background jobs (chunked state machine, Supabase only)
Supabase Edge Functions have a short wall-clock limit, so one invocation can never fetch 400 files and call the model. Every long job is a row in `jobs` (section 5) and runs as a resumable state machine. **One worker invocation does at most one step or one batch**, writes progress to the job row, and reschedules itself. No third-party queue.

- Analysis steps (`jobs.step`): `validate` → `select` → `fetch:N` (N = batch index, 25 files per batch, repeated until all selected files are fetched; each batch also scans, redacts, and extracts) → `scan` (path-based findings for denied secret files, dedupe and cap findings) → `detect` (dedupe signals, write findings and `analyses.signals`) → `ai` → `persist`. When AI is disabled, `detect` is followed directly by `persist`, which ends the analysis `done` with `error_code = AI_DISABLED`. Validation failure ends the job at `validate` with analysis status `rejected` and `error_code = PROJECT_INVALID`; the project gets `status = invalid`, `invalid_reason`, `stale = false`. On success `validate` sets the project `status = valid`, `invalid_reason = null`, `detected_kind`, `last_commit_sha = <head sha>`, `stale = false`, and `analyses.commit_sha`, `analyses.validation`. Both outcomes write `analyses.validation`.
- The `ai` step is tried at most **2 times** (not `max_attempts`) so a flaky provider can cost at most 2 billed calls; a `usage_events` row is written for every model response received. **Phase 2c (D-35):** a provider failure (timeout, network, HTTP error, unusable response envelope) ends the analysis `failed` with `error_code = AI_UNAVAILABLE` (retried once first when the cause is retryable); a response whose text is empty or `null` is `MODEL_OUTPUT_INVALID` (not retried); every failed model call or unusable model output writes one `ai.failed` server log line (`security.md` section 3). **Phase 2d (D-36):** the model call gets its own deadline, `max(step budget − 5 000, floor(step budget / 2))` ms from the start of the `ai` step, so the adapter always times out before the step timer; a step-budget abort or a database error inside the `ai` step is `INTERNAL` and writes no `ai.failed` line; the `usage_events` row is written before any abort check after a response is received.
- Generation steps (Phase 3b, D-40): `context` → `ai` → `compile` → `validate` → `persist` (Phase 4 inserts `simulate` between `validate` and `persist`; Phase 3 neither runs nor stubs it). Job `state` (`GenerateState`, worker-only, strict Zod, parsed on every read; reconfirmed D-59): `{ snippets: { path, text }[] /* ≤ 12, redacted */, signals: Signal[] /* ≤ 100 */, modelCalls: 0..3, lastProviderFailure: boolean /* the last started call ended in a provider failure */, feedback: { rule, nodeKey? }[] /* ≤ 20, our rule ids only */, spec?: FlowSpec /* the draft after checkFlowSpec */, n8nJson?: JsonValue, checklist?: SetupChecklist /* both from compile */ }`.
  - **`ai`:** when the model is `null` (kill switch, or OpenRouter refused on the Edge worker) the flow ends `failed` with `AI_DISABLED` (here it is a failure of the flow, not retried, no model call). Otherwise, **before each call** the step writes `state.modelCalls + 1` to the job row (one `updateJob`, lock held); if `state.modelCalls` is already 3 it makes no call and ends the flow (`GENERATION_EXHAUSTED`, or `AI_UNAVAILABLE` when the last started call ended in a provider failure). So every started call is counted, including timeouts, and no flow starts more than 3. The call uses the same `AnalysisModel` from `createModelFromEnv(env, runner)` as analysis (same provider switch and kill switch, D-16/D-24; OpenRouter only in the local runner, D-33; `ANALYSIS_MODEL` serves both), the same step budget and call deadline (D-35, D-36), and writes one `usage_events` row (`kind = generation`, `ref_id` = flow id) for every response received, before any abort check.
  - **Provider failure** (`ModelProviderError`): same mapping as analysis: `ai.failed` log line, `AI_UNAVAILABLE`, one retry of the step when retryable and `attempts < 2` (the R2-1 guard `attempts > 2` → `INTERNAL` applies), ended at once otherwise. The retry is a new started call and counts toward the 3.
  - **Unusable output** (empty or whitespace text, response text longer than 262,144 characters (256 KB; refused before any JSON scan or `JSON.parse`, feedback rule `F12`; D-59), no JSON object, Zod failure, FlowSpec rule failure): one `ai.failed` line (`empty_content` or `invalid_output`), the rule codes are stored in `state.feedback`, and the job stays at `ai` (`attempts = 0`, `run_after = now()`) for another call; when 3 calls are used the flow is `failed` with `GENERATION_EXHAUSTED`. `MODEL_OUTPUT_INVALID` is never a flow code.
  - **`compile`** builds the n8n JSON and the setup checklist from `state.spec` (pure, section 8) and stores both in `state`. **`validate`** runs the static validator (`testing.md`) and then `assertExportSafe` (D-50; a throw is treated like a validator failure with the `ExportNotSafeError` rule as feedback); a failure is logged as `flow.validation_failed` (rule ids and node keys only), stored as feedback, and sends the job back to `ai` under the same 3-call cap. **`persist`** writes `flows.name` (from the FlowSpec), `flow_spec`, `n8n_json`, `setup_checklist`, `catalog_version`, `n8n_version` (both always non-null on a `ready` flow, from `version.ts`; OQ-27, D-53), `status = ready`, clears `state`, and ends the job `done`. No `flow_test_runs` row is written in Phase 3.
  - Flow error codes (`flows.error_code`): `AI_DISABLED`, `AI_UNAVAILABLE`, `GENERATION_EXHAUSTED`, `GITHUB_ACCESS_LOST`, `JOB_EXPIRED`, `INTERNAL`. No new code is added in Phase 3.
- **Per-step time budget: 20 seconds.** The `ai` step budget is the model adapter's own timeout plus 5 seconds, capped at 110 seconds (Phase 2c, D-35): Anthropic 55 s → 60 s step; OpenRouter (development only) 100 s → 105 s step. The cap keeps every `ai` step at least 10 s inside the 2-minute stale-lock window (section 5), so a running model call is never re-claimed. A step that exceeds its budget aborts and the job is retried from the same step (the step must be idempotent).
- Progress: each step updates `jobs.step`, `jobs.state` (jsonb: selected paths, batch cursor, counts, redacted snippets while needed), `jobs.updated_at`, and the `analyses.progress` / `analyses.status` the user sees. Status mapping: `validate` → `validating`; `select`/`fetch`/`scan` → `scanning`; `detect`/`ai`/`persist` → `analyzing`. `progress` is an integer 0..100 that never decreases: `validate` 5, `select` 10, `fetch:N` spread evenly from 10 to 60, `scan` 65, `detect` 70, `ai` 75, `persist` 100. Generation jobs update `flows.status` only (`generating` → `ready` | `failed`).
- Scheduling: a `pg_cron` job (optional owner step, `public.kick_worker()`, Phase 2 owner setup) runs every 10 seconds and invokes the worker Edge Function over HTTP (`pg_net`) with the `WORKER_TOKEN` bearer (D-30; never the service-role key); the worker claims one job (section 5), executes one step, and if the job is not finished calls itself once more immediately (self-call) so the cron tick is only a safety net. The `POST .../analyze` and `.../generate` handlers insert the job row and trigger one worker call directly so the first step starts without waiting for the tick. **Poll kick (works without `pg_cron`):** `GET /api/analyses/:id` (and from Phase 3 `GET /api/flows/:id`) triggers one worker call (fire-and-forget) when the referenced job is `queued` with `run_after <= now()` and `updated_at` older than 15 seconds, or `running` with `locked_at` older than 2 minutes; so a chain broken by a failed self-call resumes while the user watches, and the cron tick is only needed for jobs nobody is polling. Trigger failures are logged by code only and never fail the request. **Local development (D-26, OQ-21):** `triggerWorker()` (`src/server/jobs/trigger.ts`) runs the same `runOnce` state machine in-process (`src/server/jobs/local-runner.ts`: one loop per process, at most 100 steps per kick, service-role client, same `claim_job()` locking) instead of POSTing to `/functions/v1/worker` when `runsWorkerLocally()` is true, which is exactly `process.env.NODE_ENV !== "production"`. `next build` / `next start` and Vercel always run with `NODE_ENV=production`, so deployed apps always use the Edge Function. No new env name. **D-27 (R2-2):** the local runner claims only the jobs of the user whose request triggered it: `triggerWorker({ userId })` → `kickLocalWorker(userId)` → `claim_job(workerId, userId)`; the loop keeps a set of pending user ids and drops one when its claim returns no row; it never calls `claim_job` without a user id. The Edge Function and cron path pass no user id and claim any due job.
- **Job TTL (D-29, S2-5):** `expire_stale_jobs()` (section 5) fails every job not `done`/`failed` whose `updated_at` is older than 1 hour with `JOB_EXPIRED` and clears its `state`. It runs at the start of every `claim_job()`, in the poll kick of `GET /api/analyses/:id` (when the referenced job is active and `updated_at` is older than 1 hour, before the analysis row is read for the response), and in `POST /api/projects/:id/analyze` before the active-analysis check.
- Only the worker (service role) reads or writes `jobs.state`. The user-facing `GET /api/analyses/:id` reads only `analyses`.

## 5. Data model (Supabase, RLS on every table)
- `profiles(id → auth.users, display_name, created_at, updated_at)` — row created by the `auth.users` insert trigger (Phase 0); `display_name` 1..80 chars after trim or null
- `github_installations(id, user_id, installation_id bigint, account_login, created_at)` — `unique (user_id, installation_id)`: several Flow Motion users may link the same org installation, each proven through their own `GET /user/installations` check (section 6); `installation.deleted` removes every row with that `installation_id`. Phase 1.1 security fixes (D-22) add `github_user_id bigint null`, `github_user_login text null` (the GitHub account that linked the row; null only on rows linked before D-22), and `repos_synced_at timestamptz null` (time of the last successful repo access sync for this row; null = never synced or cleared, so a refresh is required). **Phase 1.2 (D-43, D-44, D-45)** adds `account_type text null` (`'User'` or `'Organization'`, check constraint) and `account_id bigint null` (the GitHub id of the account the installation is on); both null only on rows linked before Phase 1.2, which the Phase 1.2 migration clears so they need a refresh. Check constraint `github_installations_linkable_account`: `account_type is null or (account_id is not null and github_user_id is not null and (account_type = 'Organization' or (account_type = 'User' and account_id = github_user_id)))`, so no row can hold another person's personal installation. Check constraint `github_installations_synced_has_account`: `repos_synced_at is null or account_type is not null`. Index `github_installations_github_user_id_idx on (github_user_id)`. **One GitHub account per Flow Motion account (D-44):** a GitHub account is *held* by the Flow Motion user who has at least one `github_installations` row with that `github_user_id`; no other user may link it while held (enforced in `link_github_installations()`, not by an index, because one user has one row per installation)
- `github_installation_repos(user_id → auth.users, installation_id uuid → github_installations, repo_id bigint, repo_full_name text, private boolean, default_branch text, primary key (installation_id, repo_id))` (Phase 1.1 security fixes, D-22) — the repos of that installation **the linking GitHub user can access**, exactly as returned by `GET /user/installations/{id}/repositories` at the last sync. `(installation_id, user_id)` is a composite FK to `github_installations(id, user_id)` `on delete cascade`. Index on `user_id` and on `(installation_id, lower(repo_full_name))`. `repo_full_name` check: matches the repo full name rule in section 6. `default_branch` is display-only (the branches route returns the live default). Owner-only `select` RLS; no client writes; written only by `link_github_installations()` and the webhook (service role).
- `projects(id, user_id, installation_id nullable → github_installations, repo_full_name, repo_id bigint null /* Phase 1.1 security fixes: GitHub repo id, set by POST /api/projects; null on older rows */, default_branch, branch, status[pending|valid|invalid], invalid_reason, detected_kind[website|app], last_commit_sha, stale, created_at)` — `branch text not null` (Phase 1.1, D-18) is the branch the user chose and the only branch the pipeline and webhook use; check `char_length(branch) between 1 and 255`; it is fixed after creation (to use another branch the user adds the repo again). `default_branch` is the repo's GitHub default at creation time, kept for display only. `last_commit_sha` is the head of `branch`. `unique (user_id, repo_full_name, branch)` (replaces the Phase 1 `unique (user_id, repo_full_name)`), so the same repo may be added once per branch; the `installation_id` foreign key is the one exception to the cascade rule below: `on delete set null`, so `installation_id` becomes null when the GitHub installation is removed (webhook `installation.deleted`) or disconnected in `/settings`; the UI then asks the user to reconnect GitHub before analyzing
- `analyses(id, project_id, user_id, status[queued|validating|scanning|analyzing|done|failed|rejected], progress, branch, commit_sha, files_considered, files_read, files_blocked, files_blocked_by_reason jsonb, files_skipped_budget, validation jsonb null, signals jsonb, error_code, started_at, finished_at)` — `branch text not null` (Phase 1.1) is the branch analyzed, copied from `projects.branch` by `POST .../analyze`; `commit_sha` is that branch's head at `validate`; `files_blocked_by_reason` is `{ denied, extension, size, cap }` counts (`cap` added in Phase 2; readers treat a missing key as 0); `files_skipped_budget` counts files selected but not sent to the model because of the token budget (section 4; 0 when AI is disabled); `validation` is `{ kind, reason }` written by the `validate` step; `signals` is `Signal[]` (section 6, default `[]`, max 500) written by `detect`. A partial unique index on `analyses(project_id) where status in ('queued','validating','scanning','analyzing')` allows at most one active analysis per project (Phase 2 migration).
- `jobs(id, user_id, kind[analyze|generate], ref_id, status[queued|running|done|failed], step, state jsonb, attempts, max_attempts, run_after, locked_at, locked_by, last_error_code, created_at, updated_at)` — `ref_id` is the `analyses.id` or `flows.id`; `step` and `state` are the state machine cursor (section 4). `max_attempts` defaults to 5. `state` is cleared on `done` and `failed` so no repo text outlives the job. Unique index `jobs_kind_ref_id_key on jobs (kind, ref_id)` (Phase 2 migration): one job per analysis or flow, so a repeated insert cannot create a second worker chain; plus a partial index on `jobs (locked_at) where status = 'running'` for stale-lock recovery.
- `security_findings(id, analysis_id, user_id, category, severity, file_path, line, masked_evidence, remediation)` — never raw secrets
- `security_findings.category` is one of the 11 categories in `security.md` section 6; `line` is null for path-only findings (a denied secret file that exists).
- `recommendations(id, analysis_id, user_id, title, description, trigger_kind, confidence, source_files text[], required_credentials text[], risk_level, node_types text[], rationale, estimated_tokens, status[new|selected|generated])` — `node_types` (full type names, for example `n8n-nodes-base.slack`) and `rationale` (1..400 chars) are added by the Phase 2 migration and come from the draft; Phase 3 generation uses `node_types` as a hint. **The `status` column is not written in v1 (D-41):** the DTO `status` is derived at read time from the recommendation's newest flow (section 6), so it can never disagree with `flows.status`
- `flows(id, user_id, recommendation_id, name, flow_spec jsonb, n8n_json jsonb, setup_checklist jsonb, catalog_version, n8n_version, status[generating|ready|failed], error_code, created_at)` — `ready` means the validator passed (level at least Valid); from Phase 4 the generation `persist` step also writes one `flow_test_runs` row (none in Phase 3). `name` is the recommendation title at insert and the FlowSpec name after `persist`. `flow_spec`, `n8n_json`, `setup_checklist`, `catalog_version`, `n8n_version` are null until `persist`. A recommendation may have several flows over time (failed attempts stay as rows) but **at most one that is `generating` or `ready`**: partial unique index `flows_active_recommendation_key on flows (recommendation_id) where status in ('generating','ready')` plus index `flows (user_id, created_at desc)` (Phase 3b migration)
- `flow_test_runs(id, flow_id, user_id, level[valid|simulated], passed, results jsonb, simulator_version, created_at)` — `level = simulated` only when `passed = true` with 100% branch coverage (`testing.md`)
- `usage_events(id, user_id, kind[analysis|generation], tokens_in, tokens_out, ref_id, created_at)` — log only, no limits; `ref_id` is the analysis or flow id
- `audit_log(id, user_id, action, ref, created_at)`

**Phase 1.2 replacement (D-43, D-44, D-45; new `create or replace` in `20261125120000_phase1_2_github_isolation.sql`, same signature, same grants, same return type).** Each `p_installations` item gains `accountType: string` and `accountId: number` (the GitHub account the installation is on). **RLS:** users can `select` rows where `user_id = auth.uid()`. Pipeline tables (`analyses`, `security_findings`, `recommendations`, `flows`, `flow_test_runs`, `jobs`) are written only by server code using the service role. On `jobs` the owner's `select` policy excludes the `state` column (expose it through a view or column grant, never to the client). The service role key is never imported in client code.

**Job claiming and retry:**
- Claim: in one transaction, `SELECT ... FROM jobs WHERE status = 'queued' AND run_after <= now() ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED`, then set `status = 'running'`, `locked_at = now()`, `locked_by = <worker invocation id>`, `attempts = attempts + 1`. Wrap this in a Postgres function (`claim_job()`) called by the worker.
- Stale lock: a `running` job with `locked_at` older than 2 minutes is treated as crashed and is re-queued by the next claim (same function).
- Retry and backoff: on a step error the worker sets `status = 'queued'`, `last_error_code`, and `run_after = now() + 30s * 2^(attempts - 1)` (30s, 60s, 120s, 240s). When `attempts >= max_attempts` the job becomes `failed` and the referenced analysis or flow is marked `failed` with the same `error_code`. Non-retryable errors (`PROJECT_INVALID`, `GITHUB_ACCESS_LOST`, `BRANCH_NOT_FOUND`, `MODEL_OUTPUT_INVALID` for analysis, `GENERATION_EXHAUSTED`, and `AI_UNAVAILABLE` when its cause is not retryable, Phase 2c) end the job immediately without backoff. `AI_DISABLED` is not an error: the job ends `done`.
- `claim_job(p_worker_id text) returns setof jobs` (0 or 1 row) is `security definer`, `execute` revoked from `public`, `anon`, `authenticated` (service role only). **Phase 2 review fixes:** replaced by `claim_job(p_worker_id text, p_user_id uuid default null)` (the migration drops `claim_job(text)` first so no ambiguous overload remains); when `p_user_id` is not null only that user's jobs are claimed (D-27, local runner only); it first calls `expire_stale_jobs()` (global), then the stale-lock re-queue, then the claim.
- `expire_stale_jobs() returns integer` (D-29; `security definer`, `set search_path = ''`, service role only): in one transaction, for jobs with `status in ('queued','running')` and `updated_at < now() - interval '1 hour'`: set `status = 'failed'`, `state = '{}'`, `last_error_code = 'JOB_EXPIRED'`, `locked_at = null`, `locked_by = null`; set each referenced analysis still in `queued`..`analyzing` to `status = 'failed'`, `error_code = 'JOB_EXPIRED'`, `finished_at = now()`; set each referenced flow still `generating` to `status = 'failed'`, `error_code = 'JOB_EXPIRED'`. Returns the number of expired jobs.
- `attempts` counts tries of the **current step**. After a step succeeds the worker advances `step`, sets `status = 'queued'`, `run_after = now()`, `locked_at = null`, `attempts = 0`, and the next claim picks it up.

## 7. FlowSpec (internal flow format)
```ts
// Model output (src/schemas/flowspec.ts, Phase 3a). Zod objects are strict: unknown keys fail.
FlowSpecDraft = {
  version: 1,
  name: string,                        // plain text, 3..80 chars; no leading "=", no "{{" (D-53, R3a-8; display-only in n8n)
  description: string,                 // plain text, 10..600 chars; no leading "=", no "{{" (D-53)
  nodes: { key: string,                // ^[a-z][a-z0-9_]{0,39}$, unique
           nodeType: AllowedNodeType,
           label: string,              // ^[A-Za-z0-9][A-Za-z0-9 _-]{0,59}$, unique (case-insensitive); becomes the n8n node name
           params: Record<string, JsonValue>,   // must pass the node profile's strict Zod schema (node-catalog.md "FlowSpec parameters")
           sourceFiles?: string[],     // entries not in the recommendation's source_files are removed
           notes?: string }[],         // plain text, at most 300 chars
  edges: { from: string, to: string, output?: number, input?: number }[],   // output index for IF / Switch / SplitInBatches (default 0); input index for Merge (default 0)
  tests: TestSpec                      // see testing.md; shape-checked in Phase 3, executed from Phase 4
}
// Stored in flows.flow_spec. requiredCredentials is computed by code from the node profiles, never taken from the model.
FlowSpec = FlowSpecDraft & { requiredCredentials: { type: CredentialName, usedBy: string[] /* node keys */ }[] }
```
**FlowSpec rules** (`checkFlowSpec(draft) → { ok: true, spec } | { ok: false, errors: { rule, nodeKey? }[] }` in `src/lib/flowspec/`, pure; run in the generation `ai` step after Zod; a failure uses up one model call). Each rule has a stable id used in logs and retry feedback:
- `F1` 1..40 nodes; keys unique; labels unique. `F2` every `nodeType` is in the allowlist. `F3` exactly one trigger (`manualTrigger`, `webhook`, or `scheduleTrigger`), and nothing connects into it.
- `F4` every edge references existing keys; `output` / `input` are below the node's output / input count from its profile (`switch`: number of cases, plus 1 with `fallback`); no duplicate edge. `F5` every node is reachable from the trigger. `F6` no cycles, except a loop that leaves `splitInBatches` by output 1 (`loop`) and returns to its input.
- `F7` `params` passes the node profile's strict Zod schema. `F8` every text value follows the text and expression rules below. `F9` no secrets: the secret scanner over the **shared scan rendering** of the draft (`security.md` section 9 "Scan rendering", D-49) finds nothing. `F10` `respondToWebhook` only in a flow whose trigger is `webhook` with `respond: "respondNode"`, and such a webhook flow has at least one `respondToWebhook`.
- `F11` `tests` passes the `TestSpec` shape (`testing.md`): at least one case, `trigger.kind` equals the trigger node's kind, every key in `mocks` / `expect` is a node key, `reachedNodes` is not empty. `F12` the serialized FlowSpec is at most 256 KB.

**Value types used by node profiles (D-39):**
- `Text`: a string of at most 2,000 characters that **does not start with `=`**, contains no control characters except `\n`, **does not contain `://` (any case; D-51, S3a-6; this includes the earlier `http://` rule, D-47)**, and in which every `{{ … }}` is a valid expression of the subset below (an unbalanced `{{` or `}}` fails). Text without `{{` is a literal. A link to the user's app is written with a placeholder, for example `YOUR_APP_URL/orders/{{ $json.id }}`.
- `Value`: `Text | number | boolean`.
- `Placeholder`: `^YOUR_[A-Z0-9_]{2,40}$`. **Every external destination is a placeholder, never a literal** (D-39): HTTP origins, email addresses, channels, chat ids, document, base, database and repository ids. The user replaces them after import; the checklist lists each one.
- `FieldName`: `^[A-Za-z_][A-Za-z0-9_]{0,63}$`. `FieldPath`: 1..6 `FieldName`s joined by `.`. `Ident` (SQL table or column): `^[a-z_][a-z0-9_]{0,62}$`. **Reserved names (D-49, R3a-3 / S3a-8):** `__proto__`, `constructor`, and `prototype` are refused as a `FieldName`, as any part of a `FieldPath`, and as an `Ident` (exact match, case-sensitive), the same names the expression paths already refuse.
- **Expression subset** (the only grammar; anything else fails `F8` and validator rule 6):
  ```
  expr    := operand ( cmp operand )?
  operand := ref | string | number | "true" | "false" | "null"
  ref     := "$json" path | "$node[" string "].json" path
  path    := ( "." FieldName | "[" string "]" | "[" integer "]" ){1,6}
  cmp     := "==" | "!=" | ">" | ">=" | "<" | "<="
  string  := single- or double-quoted, at most 100 chars, no quotes, backslashes, or line breaks inside
  ```
  `$node["<label>"]` must name the label of a node that is upstream of the node using it. No function calls, no method calls, no `$env`, `$execution`, `$workflow`, `$vars`, `$secrets`, no arithmetic, no template nesting. Path segments (`.name` and `["name"]`) may not be `__proto__`, `constructor`, or `prototype` (D-47).

These are the same rules the static validator applies to the compiled JSON (`testing.md`), so a FlowSpec that passes compiles to a Valid export; the validator is the independent second check. **Known exception (R3a-6, accepted, D-53):** `F12` measures the compact FlowSpec and validator rule 10 the pretty-printed export, which is larger; a spec just under 256 KB can pass `F12` and fail rule 10. This fails closed (the `validate` step sends rule 10 back as feedback) and real flows of at most 40 nodes are far below the limit.

**Accepted 3a implementation details (D-47, R3a-10; stricter than first written, all fail closed):** a `switch` case string is a literal (no `{{`); the validator's rule 6 also requires every `=` string to hold at least one `{{ … }}` and every `$node["…"]` to name an upstream node; rule 8 also refuses an `httpRequest` whose `authentication` is anything but `none`, or that carries `jsonHeaders` or credential-type parameters.

### RecommendationDraft (analysis model output)
Zod schema in `src/schemas/recommendation.ts`. The model returns `RecommendationDraft[]`; **at most 8 are kept per analysis** (`MAX_DRAFTS = 8`, Phase 2d, D-36; was 20). The prompt instruction reads "Return a JSON array of at most 8 automation recommendations for this repository, most valuable first." (built from `MAX_DRAFTS`).
```ts
RecommendationDraft = {
  title: string,                       // 3..80 chars, plain text
  description: string,                 // 10..600 chars, plain text
  trigger_kind: "webhook" | "schedule" | "manual",
  confidence: number,                  // 0..1
  source_files: string[],              // must be paths that were actually sent to the model
  required_credentials: string[],      // catalog credential names (for example "Slack", "SMTP")
  risk_level: "low" | "medium" | "high",
  node_types: AllowedNodeType[],       // every entry must be in the catalog allowlist
  rationale: string                    // plain text, 10..400 chars
}
```
Rules: a draft whose `node_types` contains an unknown or excluded type is **dropped** (logged as a count, not an error); a draft that fails the schema in any other way is also dropped; the analysis fails (`MODEL_OUTPUT_INVALID`) only if the whole array fails to parse. Zero surviving drafts is a `done` analysis with no recommendations (the UI shows an honest empty state), not a failure. **Cap (D-36):** every item of the array is validated (no positional cut-off); when more than 8 drafts survive, the 8 with the highest `confidence` are kept (stable: ties keep the model's order) and the rest are dropped and counted as `droppedOverCap` in the `analysis.drafts` log, never a failure. `source_files` entries not in the sent set are removed from the draft; `required_credentials` entries that are not catalog credential names (`SMTP`, `Slack`, `Discord`, `Telegram`, `Google`, `Notion`, `Airtable`, `GitHub`, `Postgres`, `Supabase`) are removed likewise. `node_types` are full names (`n8n-nodes-base.<type>`) checked against `src/lib/n8n-catalog/allowlist.ts`, which backend creates in Phase 2 from the type tables in `node-catalog.md` (the Phase 3 generator then checks it against the generated catalog). All strings are rendered as plain text, never HTML (`security.md` section 4). Surviving drafts become `recommendations` rows; `estimated_tokens` is computed by the backend, not the model.

## 8. n8n export format (compiler output)
```json
{ "name": "...",
  "nodes": [ { "id": "uuid", "name": "Unique Name", "type": "n8n-nodes-base.webhook",
               "typeVersion": 2.2, "position": [250, 300], "parameters": {} } ],
  "connections": { "Unique Name": { "main": [ [ { "node": "Next Name", "type": "main", "index": 0 } ] ] } },
  "settings": { "executionOrder": "v1" } }
```
- `type` and `typeVersion` come only from the generated catalog (`node-catalog.md`). **Pin (Phase 3a, D-47):** `N8N_VERSION = "2.49.5"`, `NODES_BASE_VERSION = "2.49.5"`, `CATALOG_VERSION = "2.49.5+fm2"` after the Phase 3a review fixes (was `+fm1`; bumped because profiles change, D-51, D-52). Every node uses the latest `typeVersion` of the pinned package (webhook 2.2; the example above).
- Node `name` must be unique because `connections` are keyed by name.
- IF: output 0 is true, output 1 is false. Other multi-output nodes: meaning comes from catalog metadata.
- Positions are auto-laid-out left to right (about 220 px between columns).
- Credentials: never include ids or secrets. **Phase 3 format (OQ-6 default, D-39): no node carries a `credentials` key at all.** The user picks the credential on each node in n8n after import; the setup checklist names which ones. If the import test shows n8n needs something else, the architect records it here.
- **Compiler (Phase 3a, `src/lib/compiler/`, pure, deterministic):** `compileFlow(spec) → { workflow, checklist }`. `name` = `spec.name`; each node: `id` = a UUID-shaped string derived deterministically from the node key (stable across runs, so golden files are stable), `name` = `label`, `type`, `typeVersion` from the generated catalog, `parameters` = the node module's `toParameters(params)`. A `Text` containing `{{` is emitted as `"=" + text` (the compiler is the only place a leading `=` is ever added); other strings are emitted as is. Top-level keys are exactly `name`, `nodes`, `connections`, `settings`. Any extra node-level field the import test proves necessary (for example `webhookId`) is added by the compiler and recorded here.
- **Layout (`src/lib/compiler/layout.ts`, also used by `GET /api/flows/:id`):** column = longest path from the trigger (loop-back edges ignored); `x = 250 + 220 × column`; within a column nodes keep their order in `spec.nodes`, `y = 300 + 160 × row`.
- **Setup checklist (built by code in the same call, never by the model):** `credentials` = one entry per catalog credential name used, with the labels of the nodes using it; `placeholders` = every distinct `YOUR_…` token in the compiled JSON with the labels of the nodes containing it, sorted by name; `warnings` = fixed sentences, in this order, each included when its condition holds: always "Review every node before you activate the workflow in n8n."; trigger is `webhook` → "n8n creates a new webhook URL on import. Copy it from the Webhook node into the service that calls it."; any `httpRequest` → "Add authentication to each HTTP Request node in n8n if your API needs it."; any `httpRequest` whose `path` contains `{{` (D-51, S3a-6) → "An HTTP Request node builds its URL path from incoming data. Make sure callers cannot reach endpoints they should not."; any writing node (`postgres` or `supabase` insert, `airtable`, `googleSheets` append, `notion`, `github`) → "This flow writes data. Try it with test data before using production."; any `emailSend`, `gmail`, `slack`, `discord`, or `telegram` → "This flow sends messages. Point it at a test channel or address first."
- The settings block, `typeVersion` values, and any top-level fields must be verified by importing into a real n8n. From Phase 3 this is done by the **dev-only / CI-only import test** (`n8n.md` section "Allowed now", D-9): a pinned n8n runs locally or in CI, every golden export from `tests/conformance/` is imported, and the test passes only if each opens with no errors. Exports carry an internal "unverified import" flag until that test passes for the pinned `n8n_version`; the flag is cleared when it passes and set again whenever the pin changes. Mechanism: the import test writes `tests/conformance/verified.json` (`{ n8nVersion, verifiedAt }`, committed; Phase 3a commits it as `{ "n8nVersion": null, "verifiedAt": null }` until the test has passed once); `importVerified = (verified.json.n8nVersion === pinned n8n version)` is computed by the backend and returned by `GET /api/flows/:id`; when false the export UI shows "Import into n8n x.y not yet verified" (plain notice, export still allowed). User-facing live testing stays NOT READY. **OQ-30 (D-53):** exports keep the minimal shape (no workflow `id`, no node `webhookId`, the resource-mapper shape the backend chose) until the first import run settles them; the backend fixes the compiler and the architect records the result here. The import test must pass once for the pinned version **before launch** (launch checklist in `status.md`), not before 3b.
- **`assertExportSafe(workflow)`** (`src/lib/validator/export-safe.ts`, D-47, D-50) throws `ExportNotSafeError` with `rule: "shape" | "size" | "secret" | "credentials" | "type"` and a message that never carries export text. Checks, in order: size ≤ 256 KB (serialized); shape (top-level `name`, `nodes`, `connections`, `settings`; no own key `__proto__`, `constructor`, or `prototype` at any depth, D-49); every node `type` is in the allowlist and not excluded (`type`, new in D-50); no node carries a `credentials` key; the secret scanner over the shared scan rendering (`security.md` section 9) finds nothing. The export route and the generation `validate` step run **both** `validateWorkflow(n8n_json, setup_checklist)` and `assertExportSafe(n8n_json)` (D-50).

## 10. Environment variable names (values never in the repo)
`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (server only), `GITHUB_APP_ID`, `GITHUB_APP_SLUG` (install URL), `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET` (both only for the one-time user authorization in the installations callback: installation ownership and the repo access sync, section 6, D-22), `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`, `ANTHROPIC_API_KEY`, `ANALYSIS_MODEL` (used for both analysis and generation), `APP_URL`, `WORKER_TOKEN` (Phase 2 review fixes, D-30: server only, random, at least 64 hex characters; the bearer for the worker Edge Function; required by the env schema only when `NODE_ENV=production`, because `next dev` runs the worker in-process); from Phase 2b (D-24) `ANALYSIS_PROVIDER` and `OPENROUTER_API_KEY` (server only, development only). Validated at startup by a Zod env schema; the app fails fast if a required one is missing (the AI names are required only as stated below).
**AI kill switch (Phase 2, D-16):** AI is enabled only when `ANALYSIS_MODEL` is a model id (trimmed, non-empty, not `disabled` in any case) **and** `ANTHROPIC_API_KEY` is non-empty. `ANALYSIS_MODEL=disabled` is the documented off value and the value in `.env.example`; while it is `disabled`, `ANTHROPIC_API_KEY` may be empty or absent and the env schema accepts that (it is required only when `ANALYSIS_MODEL` is not `disabled`). The worker treats a missing `ANALYSIS_MODEL` function secret as `disabled` (fail safe). The single check lives in `src/lib/analysis/model/config.ts` (`resolveModelConfig(env) → { enabled: false } | { enabled: true, provider: "anthropic", model, apiKey }`); no other code reads the AI env names.
**Provider selection (Phase 2b, D-24; replaces the rule above when built):** `ANALYSIS_PROVIDER` = `disabled` | `anthropic` | `openrouter` is the kill switch; missing, empty, or any other value = `disabled` in the worker (the Next env schema rejects other values at startup). `ANALYSIS_MODEL` holds the model id for the chosen provider (for OpenRouter its id, for example `vendor/model:free`); `ANALYSIS_MODEL=disabled` still disables (both switches must be on). `resolveModelConfig(env, runner)` takes a **required** second argument `runner: "local" | "edge"` (no default, no optional overload; the type forces every caller to choose) and returns `{ enabled: true, provider, model, apiKey }` only when: provider is `anthropic` or `openrouter`; `ANALYSIS_MODEL` is a model id; the provider's key (`ANTHROPIC_API_KEY` or `OPENROUTER_API_KEY`) is non-empty; and, **for `openrouter` only (D-33)**, all three of: `runner === "local"` (checked first, before any env value is read for OpenRouter; `"edge"` refuses unconditionally, whatever `NODE_ENV`, `APP_URL`, or key say), `NODE_ENV` is not `production`, **and** `APP_URL` parses as a URL whose hostname is exactly `localhost`, `127.0.0.1`, or `[::1]` (missing or unparsable `APP_URL` = refused). `runner` only restricts OpenRouter; `anthropic` behaves the same for both runners. Only two call sites exist: the in-process local runner (`src/server/jobs/local-runner.ts`, which claims only the triggering user's jobs, D-27) passes `"local"`; the worker Edge Function (`supabase/functions/worker/index.ts`, Deno, no `NODE_ENV`, claims every user's jobs) passes `"edge"`. Any failure returns `{ enabled: false }` (fail closed; the analysis ends `AI_DISABLED`); an `openrouter` **refusal** is logged once per resolve by code `AI_PROVIDER_REFUSED`, never with values or the reason's env contents; a refusal means a runner, `NODE_ENV`, or `APP_URL` guard failed (D-34). A missing key or a disabled model (`ANALYSIS_PROVIDER` or `ANALYSIS_MODEL` off) is the ordinary off state for every provider: `{ enabled: false }` with no log. Because the runner check comes first, `openrouter` on `"edge"` logs the refusal even when the key or model is missing. Keys are required by the env schema only for the selected provider. `.env.example`: `ANALYSIS_PROVIDER=disabled`, `ANALYSIS_MODEL=disabled`, `ANTHROPIC_API_KEY=`, `OPENROUTER_API_KEY=` with a comment "development only, owner test repos only (security.md section 3)". No DTO, page, or log line names the provider; the UI only knows `AI_DISABLED` or recommendations. **Env schema split (D-34, S2b-1):** the server env schema (every non-`NEXT_PUBLIC_` name, the provider enum, and any import of `model/config.ts`) lives only in the `server-only` module `src/lib/env.server.ts`; `src/lib/env.ts` holds only the client schema and `getClientEnv`, so no server env name or provider name is in `.next/static`.
The worker Edge Function needs `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `ANALYSIS_MODEL` (and `ANTHROPIC_API_KEY` only when AI is enabled) as Supabase function secrets (same names) plus the `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` that Supabase injects. From Phase 2b it also reads `ANALYSIS_PROVIDER` (`anthropic` or `disabled` only). **The Edge Function never uses OpenRouter (D-33):** it calls `createModelFromEnv(Deno.env.toObject(), "edge")`, so `openrouter` is refused unconditionally (model `null`, analysis `AI_DISABLED`, `AI_PROVIDER_REFUSED` logged by code). `OPENROUTER_API_KEY` and `APP_URL` are never set as worker function secrets on any Supabase project. The `pg_cron` tick reads the worker token and the worker URL for `pg_net` from Supabase Vault (`vault.decrypted_secrets`, names `worker_token` and `worker_url`), never from a migration file; when either secret is missing the tick does nothing. Next.js route handlers trigger the worker at `<NEXT_PUBLIC_SUPABASE_URL>/functions/v1/worker` with `WORKER_TOKEN` as bearer. **Worker auth (D-30, S2-6):** the worker function secret `WORKER_TOKEN`, the Next env `WORKER_TOKEN`, and Vault `worker_token` hold the same value; the Edge Function rejects every request (401) when its `WORKER_TOKEN` is missing or shorter than 64 characters, compares the bearer in constant time, and sends `WORKER_TOKEN` on its self-call. The injected `SUPABASE_SERVICE_ROLE_KEY` is used only for database access, never as a bearer. `.env.example` gains `WORKER_TOKEN=` with the comment "random, openssl rand -hex 32; same value as the worker function secret and Vault worker_token".
**Phase 3 adds no env name (D-40).** Generation uses the same `ANALYSIS_PROVIDER` / `ANALYSIS_MODEL` / provider key through the same `resolveModelConfig(env, runner)` and `createModelFromEnv(env, runner)`; there is no separate generation model, key, or switch, and the OpenRouter local-runner-only rule (D-33) applies unchanged. The n8n pin is a code constant (`src/lib/n8n-catalog/version.ts`), not an env value.
`GITHUB_APP_PRIVATE_KEY` holds the PEM with newlines escaped as `\n`; the loader restores them. **Test-only names (not in `.env.example`, never required):** `SUPABASE_TEST_URL`, `SUPABASE_TEST_ANON_KEY`, `SUPABASE_TEST_SERVICE_ROLE_KEY` point the RLS tests at a local `supabase start` stack; when any is unset those tests are skipped with a visible "skipped: no local Supabase" message, so build, typecheck, and the unit suite never need real values.
